**Status:** built; physical-host acceptance remains open · **Branch:**

## What this receipt proves

The node-local optical service now owns configured drives, insertion
generations, inspection publication, one-reader admission and generation-
checked eject. A cheap helper `presence` operation drives fallback polling only
while the replicated runtime switch is enabled. Disabling the switch or
shutting down revokes every insertion generation immediately.

The Linux adapter bounds helper time and output, suppresses inherited standard
input and error streams, and passes only trusted startup-config paths as typed
arguments. Non-Linux builds preserve the API and report the host adapter as an
unmet advisory requirement. Public snapshots and readiness evidence contain no
device or mount paths.

The daemon compiles the service unconditionally and exposes the authoritative
`optical_enabled` setting separately from Developer readiness. Readiness never
changes or vetoes the saved choice.

## Deliberately open acceptance

- No reachable machine has an operator-identified optical drive, so insertion,
  removal, hung kernel read and eject have not been exercised on hardware.
- The local FFmpeg build does not expose the required DVD or Blu-ray inputs.
- `plurx-optical-helper` is now an installed bounded Linux reader
  implementation. No physical drive is available to prove its navigation
  parsing, FFprobe input support, read behavior or eject ioctl.

Those facts block physical M2/M7 acceptance. They do not justify inventing a
green receipt, probing an unidentified drive, or gating the operator's switch.
