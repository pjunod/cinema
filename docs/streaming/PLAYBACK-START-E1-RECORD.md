## 1. E1a build record (2026-11-11)

Built on `claude/ps-e1a` (draft PR #1500): vendor patch 27, `confirmed_since`, `AppliedView`, the per-site route-read baseline, the applied-view metrics and the Developer card. No call site moves. Where the build departs from §4-§9, the departure and the reason:

- **DDL through any arm (§4.1):** the schema cookie decides the all-slot bump.
- **Restart (§5):** `MetadataRead` publishes the persisted applied index, so a caught-up node does not sit at index 0, failing every floor, until its next apply.
- **Route-read sites (§7).** Nine labels instead of five: `status` and `receipt` are split by the decision each read waits on (§6.1: `status.rs:39` / `:64` / `:141`; the three receipt fences / the five reads that may move).
- **Fallback reason `unregistered`** (§9-3): the mark does not register a view table.
- **`note_fact(table) -> FactInstant`** (§4.2, §4.3): the view takes the instant itself, after the acknowledgement or quorum read; an earlier one would make the floor unsound. `floor_met` also requires a held proof, so an old leader's watermark never retires an `Observed` entry.
- **SQLite hands out no stamps** (§4.2, §5, §8), and a failed SQLite read returns its error rather than asking the same store again.
- **`AppliedView::route` lands with the local route twin in E1c.**
- **Tests deferred (§8).** Replicated store-contract cases run on an embedded singleton (the three-voter contract cluster has only remote clients, which have no mark) with the validation proof. E1a covers the floor against the real mark, revocation mid-read, per-table stamps, and a replica held behind its own commit by the instance-local precommit hold (stamp current while held, stale the moment the entry applies, with no clock). Snapshot install, start-up restore, pending recovery, failed restore and restart are covered at the vendor layer. These need in-process multi-node clients with the real watermark sampler and move with the code they protect: the B1 release/takeover/activation sequence, the stale-replica release, the learner-join snapshot case, restart and leader change with routes → **E1c**; settings read-your-write through a lagging follower → **E1b**.

## 2. E1b build record (2026-11-11)

Built on `claude/ps-e1b` (draft PR #1505), revised after its adversarial review. Decisions taken for Paul and recorded: **§12-1 follows the plan** for the reads E1b moves; **§12-6** — background-worker reads stay on quorum, including those reached through a shared helper. Where the build departs from §4.3, §6.3 and §8:

- **What moves (§6.3), and what does not.** The view answers the HTTP request path and the polled pages: server info and name, features, system, Settings `GET`, Developer readiness, media-directory diagnostics, the network-priors preference (link receipts, `stored_prior`, processed-candidate admission), display-aware auto in create and stream, stream readrate, DV/HDR processing in the decision, preparation status, chapter thumbnails, cluster subtitle sources. **The planning/describe group, encoder admission (`vodencode.rs`), `vod/serve/create.rs:955, 2659`, FEL qualification and `media_pool.rs:1359` stay quorum reads.** Their helpers are reached from workers — the rate-control refresh loop, offline production, pretranscode, the fragment-index and analysis workers, the FEL title job — and from session takeover (`live_hls_recovery_enabled`, an ownership step); two run under a lock a save takes. Classifying them at the helper means splitting each into a request and a worker entry point, which is the planning-read work D3 does when it collapses planning onto `AppliedView::settings` with the digest (§4.2, §6.3 "stays in E1"). `remote_placement_ready` admits a forwarded start and picks the ingress placement before either allocates, so it precedes a reservation. The six sites the first build kept also stay (boot-only optimisation report; ceiling sampler, cache-preparation budget, telemetry refresh as workers; the Source copy policy in the phase-2 lane).
- **The settings floor is raised by the writers (§4.3).** Every replicated statement that may write `settings` arms a guard, classified from its SQL: a direct `INSERT`/`REPLACE … INTO`, `UPDATE [OR …]` or `DELETE FROM`, or a write to a table whose trigger writes `settings` — `subtitle_translation_commands` (any write) and `background_job_commands` (only with the trigger's `WHEN` literal `'subtitle_managed_config'`). The store's `TimedClient` arms it for every write method; the membership manager's `FlooredClient` arms the same floor (handed over as `SettingsWriteFloor`) for the reduction reference, the removal owner fence and the Live TV activation tuple it writes itself. The guard raises the floor when the write returns or is dropped. A write that commits only after its guard dropped (it timed out here) is not covered: read-your-write is owed for acknowledged writes. Pins: every `TimedClient` write method arms before the write and drops after it (any visibility, nine methods); a census over every trigger definition keeps the trigger list exact and its discriminator unbound; a census over every production SQL text in both crates fails on a settings writer outside the store, `FlooredClient`, the rusqlite restore path and the backup anchor (`WHERE 0`, no row); the store's raw-client writes are schema installation at bootstrap only.
- **Memo (§4.3), revised.** A snapshot (the polled pages) loads the whole table and reloads it when stale; keyed reads answer from the memo while its stamp is current and otherwise read their keys locally, without a reload. A snapshot that finds a reload in flight answers from Authority (new reason `reload_in_flight`, §9-3) instead of waiting, so a slow or failing reload convoys nobody.
- **Settings-as-KV churn (review S5).** Writers of `settings` other than saves: backfill cursors and done-stamps and job run times (`state.rs`, per batch or per run), Curator cover origins (per enriched item, bursty), publication and DV-queue admission keys, subtitle translation and transcription configuration (operator actions). Each raises the floor on the node that wrote it — about one watermark period of quorum reads there, today's behaviour — and makes every node's memo stale; a keyed read then costs one local keyed read, a snapshot one reload. Not measured here (no fleet run): read `plurx_applied_view_table_changes_total{view="settings"}` and the `reason="floor"` share after deploy (§9-3). Kept in the floor because a key a worker writes may be one a request reads; moving cursors and stamps to a job-state table is a separate follow-up.
- **Tests (§8).** Read-your-write through a lagging replica is built: an in-process learner beside two child voters saves through its own store while its own apply of that save is held, with a serving proof confirmed past what it applied; its view answers the saved value from Authority while its replica still holds the old one, and from the view once the entry applies (`applied_view_follower_save_never_reads_its_stale_replica`). The daemon-level `PUT /api/v1/settings` through a lagging follower is the one case deferred, to E1c's daemon harness; the store-level case above and the inventory's pin that the `PUT` response is the one Authority call of `settings_dto` cover it until then.
- **Inventory (§6.3)** is pinned by function over every production file: each view read, each direct caller of a view-reading helper, every `AppliedView` handle named `applied`, and no read or helper call in a fence, ownership, worker or boot file. The caller check is one level deep.

## 3. E1c build record (2026-11-12)

Built on `claude/ps-e1c` from `main @ 640c6bee8`: the route view and the route cache over it (§4.4, §6.1). No PR, deploy or CI run from this lane.

**Fleet baseline (E1a, `7929c2439`), the numbers E1c is sized on.** nynuc, 38,126 s up, `plurx_media_session_route_reads_total{source="authority"}`: verdict 8,313 · control 4,252 · routing 3,854 · status_first 3,649 · status_bracket 3,649 · receipt_candidate 2,172 · receipt_fence 1,262 · observer 0 — 27,151 in all; m6 has the same shape (991 · 892 · 429 · 215 · 215 · 255 fence · 255 candidate · 1). Lookups: cache_hit 2,156, single_flight 12, store 3,854. Playback quorum reads 52,307 over 9,187 playback requests (5.7 per request); route reads are ~52% of them. `plurx_applied_view_table_changes_total{view="route"}` 3,407 (~1 per 11 s); settings view 2,306 reads ok, 2 floor fallbacks. Read pool: 323,083 of 323,114 waits ≤ 0.1 ms.

**Decisions taken for Paul (recorded in §12).** §12-4: accept the measured floor — the sites E1c moves (routing, status_first, observer) are ~28% of route reads and ~14% of playback quorum reads; verdict, control, status_bracket and the receipt fences stay (~64% of route reads); redesigning those brackets is a follow-up, not E1. §12-5: `status.rs:39` moves view-first. §12-7: per-table invalidation — the read-pool wait shows no contention. The five `receipt_candidate` reads (`link_receipts.rs` accept, accept_negative_for_ack, current_positive_until ×2; `prepared_link.rs` register) stay: 8% of route reads, not worth a per-site claim-free proof.

**Built.**
1. `HiqliteAuthStore::local_media_session_route` — `route_by`'s projection as a local read — run by `AppliedView::route` only while `media_session_projection == 2`; otherwise Authority, reason `legacy_layout`.
2. `raw_route_before` reads `read_media_session_route_view` (counted by site and source); its four pending-release checks are unchanged.
3. `CachedRoute { route, origin: View(stamp) | Observed { fact, at }, sequence }` with the retirement rule; a view answer never replaces an unretired `Observed` entry; past `QUORUM_WATERMARK_LEASE` one quorum read becomes the new `Observed`.
4. `ROUTE_CACHE_TTL` and the three sweeps are gone; a full cache evicts by one scan; `plurx_media_session_route_prune_entries` counts that scan.
5. `status.rs:39` view-first; any verdict other than active is confirmed by the existing `status_first` quorum read.
6. `system.rs` `prepared_seam_session_processed` (the Activity observer) reads the view.
7. `plurx_media_session_route_lookups_total{result}` gains `observed` and `view`; help text fixed.
8. The Developer "Applied view" row gives settings and route counts separately; `plurx_applied_view_reloads_total{view="route"}` counts stale-stamp re-reads.

**Departures from §4.4, and why.**
- **A route fact is per row, not a table floor.** `note_fact` raises the table floor, which would close the route view for every session on each activation or release this node publishes. The cache takes the instant from `AppliedView::observe()` and keeps it in the entry; `AppliedView::hold_floor` closes the table only when it must drop an unretired entry (eviction), so dropping an entry never lets a lagging replica answer that row.
- **Retire and replace only under the session's single-flight shard.** The first, unlocked cache check treats a retirable or expired `Observed` entry as a miss; removal happens in the second check, which holds the shard. A lookup's read in flight therefore never loses the publication it must defer to (`cache_queried_route_result`'s generation check still returns that entry).
- **Eviction's "stale" is a `View` entry whose table moved** (`AppliedView::same_image`, no per-entry proof check); otherwise the lowest insert sequence goes. An unretired `Observed` victim triggers `hold_floor`.
- **SQLite:** a view answer carries no stamp, so it is returned and not cached; every lookup on SQLite is one local primary-key read (§4.2 "Standalone"). Single flight still serialises a capability's lookups.
- **`QUORUM_WATERMARK_LEASE` is public** so the cache uses the proof's own constant; `serving_proof_remains_valid`'s comment now says the applied views read under the proof (§4.2 nit 1).
- **The status first read is counted `status_first`**, view or authority, through `status_view_media_route_resolution_before`; the confirming read is the existing quorum read under the same site.

**Tests.** Store contract (`store_contract/applied_view.rs`): `applied_route_view_on_sqlite_is_the_store`; `applied_route_view_moves_with_a_release_applied_here` (singleton: stale the moment a release applies, no clock; another session's write moves the slot too); `applied_route_view_answers_authority_in_the_legacy_layout`; `applied_route_view_never_meets_the_floor_of_a_release_its_replica_holds_back` (B1 at the store layer on a lagging learner: the raw view answers the pre-release row, the per-row floor stays unmet without closing the table, `hold_floor` closes it). Daemon (`media_sessions/route_view_tests.rs`, through a replica double): no clock in a `View` entry; a peer release applied here; the B1 sequence through the cache for release, takeover and activation; degraded mode one quorum read per session per lease; a 4,096-id miss storm with no quorum read; eviction at capacity; a fence never calls the view (runtime double and source); single flight. Inventory (`http/applied_route_inventory.rs`): every Store route read by function and site, every view read, every caller of the cached lookups, the Store method called from one place, status view-first with its quorum bracket.

**Not built here.** The daemon-level `PUT /api/v1/settings` through a lagging follower (deferred from E1b) and the learner-join snapshot, restart and leader-change cases with routes (deferred from E1a): plurxd's unit tests cannot build an in-process replicated follower (the validation features are plurx-core's), and no daemon harness exists for one. The route view shares `check`, the generation guard and the proof with the settings view, whose snapshot and restart behaviour the vendor tests cover. A two-node `cluster-integration-tests` case is the place for them.
