## 3. Steps — one complete Wave 1 PR

### 3.1 Prove where identities diverge

Map selected recipe -> local identity -> shared pipeline digest -> job claim
-> generated bytes -> blob header -> hydrated FragmentIndex -> VOD init/plan.
Use the existing DV fixture and small synthetic streams. Check output-affecting
Rust conversion as well as FFmpeg argv: two transforms with the same argv
cannot share a key if their fragment bytes differ. Include transform revision
when it changes generated bytes. Preserve keys for unchanged ordinary recipes
where the old key is already complete and correct.

Record the map in the PR, including whether a blob-format change was needed.
Do not add a second persisted recipe catalog if the existing digest and
selected job identity already carry the necessary distinction.

### 3.2 Produce and distribute the exact branch

Use video_identities for producer branch selection and compare the claimed
job's digest to supported exact outputs. The selected source descriptor and
attestation must remain held through generation. Publish a catalog artifact
only after generation and blob verification succeed under the current lease.
Lease loss, replacement or cancellation cannot publish stale results.

Coalesce jobs by exact source/recipe identity. A stripping artifact may remain
valid for a stripping consumer, but cannot satisfy a DV conversion consumer.
Hydration must preserve promotion/init metadata and reject mismatched source,
recipe, corrupt contents and unsupported formats. If a peer cannot supply a
verified artifact, use the existing exact repair job; keep local fallback
compatible while that work completes.

### 3.3 Close the consumer path

Remove the broad preserved-DV early rejection only after §3.2 works. Resolve
the actual selected recipe, not the first identity in video_identities. A miss
continues to produce a truthful pending/unavailable outcome; the coordinator
owns the broader first-play behavior. No successful lookup may change codec,
resolution or dynamic range from the selected recipe.

### 3.4 Focused proof, commit and PR

Use existing tests where they exercise the behavior; add only missing cases:

| Case | Required result |
|---|---|
| Strip/preserve/convert from one source | Different keys whenever output differs |
| Host input path differs, same attested source and recipe | Shared identity remains portable |
| Transform changes without FFmpeg argv change | Different identity if output changes |
| Blob round-trip for converted recipe | Promotion/init/fragment metadata retained |
| Peer hydration with no local v1 index | Exact DV copy VOD can be created |
| Wrong recipe or corrupt blob | Refused; no metadata substitution |
| Duplicate request, lease loss, source replacement | Existing job/fence semantics remain correct |
| Ordinary existing artifact | Reusable where its identity remains valid |

Run the pinned compile/clippy/format checks plus the smallest actual test
filters covering changed modules. Use --list to confirm filter selection if
needed, then run each focused set once per relevant candidate. Do not run the
workspace unit suite repeatedly. Put commands, counts and exit status in the
PR. Request no adversarial agent review; the coordinator will arrange the
single final review on the main-bound PR.

Commit normally, update this handoff's result section in that commit, push
codex/streaming-shared-index (or a collision-free codex branch), and open a PR
into effort/streaming-reliability. Do not merge it yourself. Send root-reference
and validation-catalog changes needed to the coordinator; apply coordinated
updates before task merge. Do not independently edit docs/README.md.
