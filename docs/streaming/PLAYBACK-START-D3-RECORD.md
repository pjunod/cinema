## 3. Decisions taken

1. **The label is the Store method name, set at the call site, forwarded by wrappers.** Every helper that stands where a Store method does takes the label and forwards it: the eight first found (`activate_with_authority`, `desired_row`, `live_local_route`, `scalar`, `pairs`, `watch_query`, `watch_write`, and `session_layout`'s plumbing) and, after review S1, the generic ones named in §1-1. `session_layout` itself is the exception by design: its reads carry the label `session_layout`. Taken: file:line never reaches a metric.
2. **Labels that are not a Store method, and why.** The allow-list `NOT_A_STORE_METHOD` holds them, each with a reason, and the census fails on any other. The queue bridge (`queue_sql`, `queue_transaction`) keeps its own name: its callers are generic over `QueueSql`, shared by both stores and the background-jobs code that the formal packages pin, and threading a label through them touches every body function for attribution no D3 step needs; its create-path writes are named in the table by what they are. Schema migration, import and digest helpers carry their function name; so do the sharing `Backend` trait's `sharing_read` and `sharing_txn` (shared with the SQLite store, 458 call sites, none on the playback path: forwarding a Store method through it is deferred with the rest of sharing attribution), the live-TV ledger's two `Backend` operations, and the throttled last-seen writes the auth lookups trigger. Eleven consistent reads are made on the raw vendor client or its one `TimedClient` wrapper (bootstrap, compatibility and shape probes): they never reach a request's counts (a few, such as the committed-schema-version read, can run on a live store but never inside a request's scope), cannot carry a label, and are pinned per slice in `RAW_CLIENT_SITES` so a new one fails the census until it is labelled or added on purpose.
3. **The file:line debug log is not built.** `#[track_caller]` does not carry through async functions and `async_trait` Store methods, so a call-site location would need a second argument at every site. The label already locates the Store method; the SQL statement locates the rest. A later lane that needs the line can add `file!()`/`line!()` to a trace event at the same sites.
4. **For Paul: count the Confirm write once?** `execute_idempotent` is the only wrapper that times a write at two layers. Counting it once would make the pinned totals 5/7/7/8 and `plurx_http_store_reads_total{class="write"}` one lower per create; D3a did not, because the contract says the totals stay. The coordinator's §9-1 "writes unchanged" holds either way; say which spelling the acceptance should use.
5. **The owner start now has a Store-operation scope.** A task spawned by `ims.rs::start` did not inherit the request's task-local counts, so a remote owner's own planning, settings, probe and file reads were counted nowhere. The start task now runs inside the request's scope and logs its own window (§7.1-2). `plurx_http_store_reads_total{route_group="cluster"}` therefore rises by the owner's start operations: attribution, not new reads. **Baselines must be taken on a D3a-or-later build:** from this landing the owner-start scope adds the remote owner's operations to `route_group="cluster"`, so the 2026-11-07 `cluster` figure and any E1 before/after pair that straddles the D3a deploy are not comparable (review S6; the same note is in the E1 record. `docs/OPERATIONS.md` does not describe this metric and is at its size ceiling, so it carries none). The task is spawned through `spawn_in_http_store_scope`, which carries the request's counts in; `a_spawned_start_counts_into_its_own_request_and_a_bare_spawn_counts_nowhere` proves the window counts the owner's operations, that a bare `tokio::spawn` counts nothing (the failure mode), and that the owner's count is on the internal request it serves and on no other. Why a read absent from the window is not silently counted as saved (review S4): the window is the start task's own body, §9-3's "0 planning, settings, probe and file reads" is read from it, and a read in a task spawned inside the start without the scope would be absent; none exists today (the confirmation watcher makes one route read after the response, and the activation and abort tasks are not start reads, all deliberately unscoped and commented), and the helper is the one way the code spawns a start so that a later spawn is written the same way. D3b, which moves reads, must keep that rule and may compare the window's total with the owner process's own `plurx_http_store_reads_total` delta over the same interval on the cost-validation build.
6. **Per-request cap 128, process cap 4096.** The widest create measured touches 19 methods (reopen, with `session_layout`); the caps bound a mistake, and the overflow is visible (`other`, `…_dropped_total`).
7. **No `StoreMethod` newtype** (review N2, skipped). `method: &'static str` beside `sql: Into<Cow<'static, str>>` lets a swapped pair compile; the consistent-read census catches that for consistent reads, and a newtype would touch ~700 call sites again for a mistake a run of the path shows at once. Deferred as churn; revisit if a swapped pair ever ships.
8. **Confirm is double-timed** (review N3). The pin's `settle_media_session_activation (1, 0, 2)` is one physical `UPDATE` timed twice; the pin carries a comment saying so, and counting it once is Paul's call (decision above).

## 6. D3t build record (2026-11-12)

Built on `claude/ps-d3t` from `claude/ps-e1c-d3a`. §4.1 exactly: additive triggers that bind every planning key to `playback_input_generation`, on both stores, with a pinned key list. `PLAYBACK_INPUT_SCHEMA` is untouched and no schema version moves on either store (the cluster version and SQLite `user_version` 128 are as before). The adversarial review ([PLAYBACK-START-D3T-REVIEW-2026-11-12.md](../reviews/PLAYBACK-START-D3T-REVIEW-2026-11-12.md)) found two blockers; both are fixed and the rest dispositioned there.

**What was built.**

- `store/playback_input_keys.sql` and `store/playback_input_keys.rs`: a marker table `playback_input_keys_schema(singleton, version >= 1)` and three revision-1 triggers, `playback_input_keys_r1_insert`, `playback_input_keys_r1_update` (new or old key in the list) and `playback_input_keys_r1_delete`, each running the same `UPDATE playback_input_generation SET generation = generation + 1` as the glob triggers. New names, so old binaries ignore them and they keep firing after a rollback.
- Hiqlite: an extension installed beside source arbitration and analysis coordination, at bootstrap and on every `SchemaMigrationAction::Current` open (`install_playback_input_keys_schema`). `playback_input_keys_shape` compares every revision-1 object's SQL with what SQLite itself stores for the canonical text (`schema_objects`), refuses a partial or mutated shape, and requires the committed marker (version 1 or later). The install is one replicated transaction guarded by a raced-install check over the exact object names; settlement is by re-reading the shape. Both shape reads carry the method label `playback_input_keys_shape` (allow-listed as startup in the label census) and an `// authority:` reason.
- SQLite: `playback_input_keys::install_sqlite`, called from `SqliteStore::init` after `migrate`. It installs the same SQL in one transaction when none of the objects exist, leaves a complete shape alone, and refuses a partial or mutated one, the same exact-shape rule as hiqlite. It takes no `MIGRATIONS` ordinal: `user_version` stays 128, an older binary opens the database and ignores the objects, and the three ordinal pins (`v6_rebuild_preserves_everything`, `the_downgrade_fixture_undoes_every_migration_after_the_guard`, the coordination tail rewind) stay true.
- Fixtures: the two wind-back fixtures (`sqlite_v43_guard_migration_refuses_an_unrecoverable_committed_claim`, `populated_v14_import_fixture`) and the hiqlite `validation_set_schema_lineage` downgrade drop the new triggers and marker beside `playback_input_generation`; the reopen reinstalls them.
- Tests, both stores: `store_contract::every_planning_key_write_moves_the_playback_input_generation` writes (insert, update, delete) every key of `PLAYBACK_PLANNING_KEYS`, every key of the extension and a representative of each glob family, asserting the generation moves, and that a `jobs.*` key does not. Delete goes through a raw handle (`StrandedFieldOrder::delete_setting`) because the Store trait has no setting delete. Core unit tests on raw SQL: `every_bound_key_moves_the_generation_and_others_do_not` (insert, update, delete, rollback, renames into and out of the list, a no-op write, idempotent install), `the_predicate_and_the_triggers_describe_the_same_set` (the Rust `starts_with` predicate against the real glob and extension triggers over every planning key, every extension key, glob edge cases and unrelated keys), `a_partial_shape_is_refused_and_a_later_revision_is_tolerated`.
- Pins: `the_extra_key_list_is_pinned` (the literal list, sorted, none inside a glob), `the_sql_names_exactly_the_pinned_keys` (four IN-lists, same list). In `plurxd` (`transcode/manager/candidates.rs`): `every_planning_key_moves_the_playback_input_generation` (every `QUALITY_PLANNING_KEYS` entry is covered by a glob or the extension), `the_store_contract_key_list_is_the_planning_list` (the core copy the contract test loops over equals `QUALITY_PLANNING_KEYS`; D3b widens both) and `every_setting_the_create_chain_reads_is_bound_or_excluded`, a source scan of the create-chain files (`transcode/manager/{create,describe,start}.rs`, `http/hls/create.rs`, `media_pool.rs`, `subtitle_source.rs`, `vodencode.rs`, production text only): every `keys::NAME` in them, resolved to its value from the `keys` module, must move the generation or be on `UNBOUND_CHAIN_READS` with a reason. A setting a later lane makes the create read fails the scan until it is bound or excluded.

## 7. D3t decisions

1. **No schema version moves on either store.** The first build took SQLite v129 on the reasoning that SQLite has no extension mechanism; the review showed an idempotent step after `migrate` does the same job without an ordinal, keeps `user_version` 128 (so a standalone node can still roll back and the three ordinal pins hold), and gives SQLite the same exact-shape check as the replicated store. Decided by the coordinator.
2. **The list is six keys.** The contract named the three outside-glob keys already in `QUALITY_PLANNING_KEYS` plus "what D3b widens it by". The two cluster switches are what D3b adds (typeless playlist, placement) and `subtitles.stored_sources` is what the burn guard reads; they are bound now so D3b needs no second trigger change.
3. **Deletes are tested through a raw handle.** The Store trait has no setting delete; the contract test adds a raw delete helper rather than a trait method that no production caller wants.
4. **Co-author line.** Commits carry the session's `Claude Sonnet 5.5` attribution (the model that built them), not the `Claude Opus 5.5` line the E1 brief quotes.
5. **Two more `query_consistent` sites (67 to 69).** Contract §2 says D3 adds none. The extension's shape and marker reads are the two, as `source_arbitration_shape` has; both are startup-only, labelled, and allow-listed as startup. The consistent-read census row for `hiqlite.rs` rises to 69 accordingly. Unavoidable with the precedent; recorded as a departure.
6. **A no-op write moves the generation.** `put_setting` with the same value, and the import path's `UPDATE settings SET updated_at …`, fire the update trigger, exactly as the glob triggers already do. The cost is one extra owner refusal and re-plan; the safe side. Since the `cluster.*`, `cache.max_gb` and `vod.*` switches are now bound, an operator re-saving an unchanged value re-plans a start in flight.
