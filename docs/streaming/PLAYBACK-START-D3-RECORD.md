What §7.1 asked for, and what was built:

1. **Store-method label on every operation.** `TimedClient::{query_consistent_map[_scoped], query_map, execute, execute_acked, execute_idempotent, source_layout_idempotent, execute_returning_map[_acked,_one], txn, txn_source_layout_attempt, batch}` take `method: &'static str` first. The label is the name of the Store method; `SessionClient::{query_consistent_map, execute, execute_idempotent, txn, attempt}`, `route_by`, `request_row`, `session_layout`, `activate_with_authority`, `desired_row`, `live_local_route`, `scalar[_with]`, `pairs`, `local_scalar`, `local_pairs`, `watch_query`, `watch_write[_returning]` forward their caller's label. The remaining ~700 call sites were labelled mechanically from the compiler's arity errors (the label is the enclosing function's name). Review S1 then found that the generic helpers still stamped their own name on every caller, so `execute`, `execute_idempotent`, `atomic_publication`, `credential_mutation`, `user_optional`, `key_optional`, `query_channel`, `request_ledger_full`, `rows`, `staged_row`, `recovery_row`, `commit_replay`, `claim_from_row`, `claim_existing_or_reacquire`, `route_projection` (through `LocalSessionSql::load`), the `read_watch_*` readers and the remaining catalog and fragment-index helpers now take `method` and forward it. Two census rules hold it: a consistent read's first argument is an identifier-shaped literal or the forwarded `method` (`every_consistent_read_names_its_store_method`), and every label in `STORE_SOURCES` is a method declared in a `Store` trait, the `local_` twin of one, or a function in the named allow-list `NOT_A_STORE_METHOD`, each entry with its reason (`every_label_names_a_store_method`; `the_label_allow_list_has_only_live_entries` keeps the list from rotting; `the_label_rule_refuses_a_helper_name_and_admits_store_methods` proves a helper-name label fails). The census also counts raw-client reads spelled through `inner()` or as `Client::query_consistent_map(..)`, and fails on a site it cannot parse instead of skipping it.
2. **Request-scoped counts.** `HttpStoreOperationCounts` keeps a per-method (local, authority, write) map beside the totals, bounded at 128 methods per request (`MAX_METHODS_PER_REQUEST`; the rest fold into `other`). The create budget line logs `methods=name=authority/local/write,…` for its own window (`method_snapshot_since`). The owner's `ims.rs::start` logs `remote start store operations finished` with `incarnation_id` and `methods=`.
3. **Metric** `plurx_http_store_operations_by_method_total{route_group,class,method}`, emitted only for series that exist. **Bound:** labels are `&'static str` chosen at Store call sites, so the set is bounded by the source (about 470 distinct labels today); series are `route_group × class × method`, but a method is issued in one or two classes from two or three groups, so the live series number a few thousand at most; the exposition holds at most `HTTP_METHOD_SERIES_CAP = 4096` series and counts anything past it in `plurx_http_store_operations_by_method_dropped_total`. `the_by_method_series_are_capped_and_the_overflow_is_counted` pins the cap and the drop counter. At the cap the series that arrived first are the ones kept, permanently until restart, and the dropped counter is what says a reading is incomplete.
4. **Per-shape pin** (`create_path_store_operations_are_pinned_per_shape`): every method's (authority, local, writes) per shape, the split-sums-to-total check, and the fifth shape (caps-v2 Auto with an intent).
5. **Formal mappings.** `store/hiqlite.rs` and three more pinned files changed; `scripts/check-formal check-mapping` for durable-jobs and operation-progress listed the drift (worker-refinement unaffected). The review is in the commit message. In short: the anchored text is unchanged in every row (each anchor occurs once in the reviewed blob and once now; durable-jobs lists 20 rows and operation-progress 5 of the drifted ones, 25 row listings in all, which the first commit message counted as 24 anchored regions because one source anchor is cited by both packages); `hiqlite_background_jobs.rs`, `hiqlite_coordination.rs` and `hiqlite_publication.rs` are identical to the reviewed blob modulo inserted label literals, whitespace and trailing commas; in `hiqlite.rs` the anchored `txn` and `STORE_TIMEOUT` text is unchanged and its body only forwards `method`.

## 3. Decisions taken

1. **The label is the Store method name, set at the call site, forwarded by wrappers.** Every helper that stands where a Store method does takes the label and forwards it: the eight first found (`activate_with_authority`, `desired_row`, `live_local_route`, `scalar`, `pairs`, `watch_query`, `watch_write`, and `session_layout`'s plumbing) and, after review S1, the generic ones named in §1-1. `session_layout` itself is the exception by design: its reads carry the label `session_layout`. Taken: file:line never reaches a metric.
2. **Labels that are not a Store method, and why.** The allow-list `NOT_A_STORE_METHOD` holds them, each with a reason, and the census fails on any other. The queue bridge (`queue_sql`, `queue_transaction`) keeps its own name: its callers are generic over `QueueSql`, shared by both stores and the background-jobs code that the formal packages pin, and threading a label through them touches every body function for attribution no D3 step needs; its create-path writes are named in the table by what they are. Schema migration, import and digest helpers carry their function name; so do the sharing `Backend` trait's `sharing_read` and `sharing_txn` (shared with the SQLite store, 458 call sites, none on the playback path: forwarding a Store method through it is deferred with the rest of sharing attribution), the live-TV ledger's two `Backend` operations, and the throttled last-seen writes the auth lookups trigger. Eleven consistent reads are made on the raw vendor client or its one `TimedClient` wrapper (bootstrap, compatibility and shape probes): they never reach a request's counts (a few, such as the committed-schema-version read, can run on a live store but never inside a request's scope), cannot carry a label, and are pinned per slice in `RAW_CLIENT_SITES` so a new one fails the census until it is labelled or added on purpose.
3. **The file:line debug log is not built.** `#[track_caller]` does not carry through async functions and `async_trait` Store methods, so a call-site location would need a second argument at every site. The label already locates the Store method; the SQL statement locates the rest. A later lane that needs the line can add `file!()`/`line!()` to a trace event at the same sites.
4. **For Paul: count the Confirm write once?** `execute_idempotent` is the only wrapper that times a write at two layers. Counting it once would make the pinned totals 5/7/7/8 and `plurx_http_store_reads_total{class="write"}` one lower per create; D3a did not, because the contract says the totals stay. The coordinator's §9-1 "writes unchanged" holds either way; say which spelling the acceptance should use.
5. **The owner start now has a Store-operation scope.** A task spawned by `ims.rs::start` did not inherit the request's task-local counts, so a remote owner's own planning, settings, probe and file reads were counted nowhere. The start task now runs inside the request's scope and logs its own window (§7.1-2). `plurx_http_store_reads_total{route_group="cluster"}` therefore rises by the owner's start operations: attribution, not new reads. **Baselines must be taken on a D3a-or-later build:** from this landing the owner-start scope adds the remote owner's operations to `route_group="cluster"`, so the 2026-11-07 `cluster` figure and any E1 before/after pair that straddles the D3a deploy are not comparable (review S6; the same note is in the E1 record and OPERATIONS.md). The task is spawned through `spawn_in_http_store_scope`, which carries the request's counts in; `a_spawned_start_counts_into_its_own_request_and_a_bare_spawn_counts_nowhere` proves the window counts the owner's operations, that a bare `tokio::spawn` counts nothing (the failure mode), and that the owner's count is on the internal request it serves and on no other. Why a read absent from the window is not silently counted as saved (review S4): the window is the start task's own body, §9-3's "0 planning, settings, probe and file reads" is read from it, and a read in a task spawned inside the start without the scope would be absent; none exists today (the confirmation watcher makes one route read after the response, and the activation and abort tasks are not start reads, all deliberately unscoped and commented), and the helper is the one way the code spawns a start so that a later spawn is written the same way. D3b, which moves reads, must keep that rule and may compare the window's total with the owner process's own `plurx_http_store_reads_total` delta over the same interval on the cost-validation build.
6. **Per-request cap 128, process cap 4096.** The widest create measured touches 19 methods (reopen, with `session_layout`); the caps bound a mistake, and the overflow is visible (`other`, `…_dropped_total`).
7. **No `StoreMethod` newtype** (review N2, skipped). `method: &'static str` beside `sql: Into<Cow<'static, str>>` lets a swapped pair compile; the consistent-read census catches that for consistent reads, and a newtype would touch ~700 call sites again for a mistake a run of the path shows at once. Deferred as churn; revisit if a swapped pair ever ships.
8. **Confirm is double-timed** (review N3). The pin's `settle_media_session_activation (1, 0, 2)` is one physical `UPDATE` timed twice; the pin carries a comment saying so, and counting it once is Paul's call (decision above).
