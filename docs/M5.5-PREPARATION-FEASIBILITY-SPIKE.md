## 1. The answer already on the wire is a placeholder, and it says no

Start here, because it changes what this spike is.

`dual_player_preparation` is **already a field in the frozen
`plurx-playback-control-v1` capability set** — `DynamicCapabilities`,
`crates/plurxd/src/playback_control.rs:392-400`, documented at
[PLAYBACK-CONTROL-PROTOCOL-M1.md](PLAYBACK-CONTROL-PROTOCOL-M1.md) and
enforced across all four ports by
`tests/validation/test_control_wire_conformance.py`.

Every client declares it as a bare `false` literal:

| platform | file:line |
|---|---|
| Apple | `clients/apple/Sources/Caps.swift:264` |
| Android | `clients/android/app/src/main/java/tv/plurx/app/player/PlaybackControlSnapshotMapper.kt:276` |
| web | `crates/plurxd/src/web/index.html:6142` |

Unlike every neighbouring capability — `max_height` carries a paragraph on why
a number it cannot back would be a claim rather than a capability — this one
carries no derivation and no comment. **Nothing on the server reads it**
either: a repository-wide search finds only the struct field and test
fixtures.

So the fleet currently tells the server, honestly-looking and in three
languages, *I cannot prepare two pipelines* — a value nobody measured and
nobody decided.

**That makes this spike a validation, not an invention.** Its output is a
correction to three hardcoded literals, and M6 must read the field rather than
re-deriving the answer. Without that, M6 can read the wire, see three `false`s,
and conclude no platform supports dual preparation regardless of what the
hardware said.

What this spike *does* freeze is the acknowledgement half (§2), which does not
exist yet.

## 2. Why the rest of it exists

M6 builds a prepared handoff: a successor stream is primed while the current
one still plays, and the switch commits only once the successor says it is
ready. **"Ready" is a promise the client makes to the server.**

> A player reporting "ready" while holding no successor buffer produces a
> commit that stalls at the switch boundary — the exact failure prepared
> handoff exists to prevent.

**An asset-metadata callback or an `AVPlayer` / `Media3` ready state is not
`buffer_ready`.** Both mean "I could start"; neither means "I have contiguous
film through the boundary." Both are already used, correctly, for a different
question — `Controller.kt:1196` maps `isLikelyToKeepUp` from
`Player.STATE_READY`, and `PlayerController.swift` maps it from
`isPlaybackLikelyToKeepUp` — which is exactly why they are the trap.

### 2.1 The three acknowledgements

| ack | means | measured how |
|---|---|---|
| `metadata_ready` | the successor's manifest/item is parsed and its decoder eligibility accepted | timestamp of the platform's parse/eligibility callback |
| `buffer_ready` | the successor holds **contiguous film time through the switch boundary, plus its measured safety runway** | §2.2's readers, at the boundary — never a ready flag |
| `first_frame_ready` | observed **only after commit**, with wall latency and film position | first *presented* frame of the successor (§3.4 — Apple has no such signal today) |

Per plan §13.6 these acknowledgements are frozen by M5.5 itself, from what is
measured here. Their field *names* are M6's to choose; their *meanings* are
this document's output.

### 2.2 Use the readers the clients already have — a raw API over-reports

All three clients already implement what `buffer_ready` means, including the
trap, and all three agree:

```swift
// clients/apple/Sources/PlayerController.swift:1585
/// Playable seconds contiguous with the current clock. A later buffered
/// island beyond a gap is not runway: AVPlayer still has to stop before it
/// can reach it.
nonisolated static func bufferedRunwaySeconds(
    playheadSeconds: Double, ranges: [ClosedRange<Double>], joinTolerance: Double = 0.25)
```

Web applies the same 0.25 s join rule at `index.html:3211`; Android takes
`bufferedPosition - currentPosition` at `Controller.kt:1178`.

**A successor item primed by seeking to a boundary routinely holds a leading
island from its initial load plus the boundary island.** An operator who reads
`loadedTimeRanges` and takes the maximum end, or sums the ranges, gets a
buffered-through number that is too large — which is the over-claim §2 says
this spike exists to prevent, arrived at by following a raw-API instruction.
Use `PlayerController.bufferedRunwaySeconds(playheadSeconds:ranges:joinTolerance:)`
and its Android and web counterparts.

### 2.3 Player time is not film time

Every one of those readers is item-local and says so:

```kotlin
// clients/android/.../Controller.kt:1174-1178
// Only the runway *ahead* is protocol runway. Media3's bufferedPosition
// is in player time while the protocol wants title time, so the range
// is reported from the playhead forward rather than converted with an
// offset a copy session's keyframe start would make wrong.
```

A successor primed at a switch boundary **starts at a different origin from
the predecessor** — plan §9.2's mapping table calls for "plus VOD/live origin
mapping" on both platforms. Record the successor's origin offset with every
buffered-through reading, or every number in the one measurement this document
calls the whole spike is wrong by that offset.

### 2.4 The safety runway is measured, and on Apple it is also calibrated

The runway is the answer to: *after the successor claims contiguous film
through the boundary, how much more does it need so the commit does not
stall?*

Measure it as the smallest runway at which **twenty consecutive commits stall
zero times**. Twenty is a floor, not a proof — twenty clean trials bound the
true stall rate at roughly 14% with 95% confidence — so state the count with
the number, and raise it for any platform whose fallback is expensive.

**On Apple the number is meaningless without its calibration.** The shipped
client sets `preferredForwardBufferDuration` per item
(`PlayerController.swift:1266`), 60 s for growing HLS and 0 otherwise, and the
repo's own notes record that AVPlayer treats it as a hint and fetched twice
it, and that a topped-up AVPlayer stops fetching for a long stretch. A
successor left at the shipped setting simply stops filling; a non-current item
fills far less.

So record, at every ack: the successor's `preferredForwardBufferDuration`, and
`isPlaybackBufferFull` (`PlayerController.swift:1636`). Without the second
there is no way to tell *the successor holds 12 s because that is all the link
gave it* from *because it hit its own cap*, and those are different results.

## 3. The procedure, per platform

Run each platform twice: once **same-codec, same grade** (a resolution/bitrate
change only — the axis plan §5.2 expects to be genuinely transparent), and
once **codec or dynamic-range change**. The second is expected to be worse;
the point is to know by how much.

Record, per attempt:

| field | unit | why it is here |
|---|---|---|
| peak memory | MB | dual pipelines double the buffer pool; phones kill apps for this |
| decoder instances | count | plan §5.3's one-slot problem is decided by this number |
| network duplication | Mbit over the prime window | two streams on one link is why a prepared handoff can cause the stall it prevents |
| old-stream continuity | stalls observed in the predecessor | **the predecessor must not suffer for the successor** |
| buffered-through at ack | ms of film past the boundary | the claim being validated — with origin offset (§2.3) and, on Apple, its calibration (§2.4) |
| switch position error | ms | film time skipped or repeated at the boundary |
| first-frame latency | ms after commit | what the viewer sees |

### 3.1 The harness you have to write, and the one you do not

Four of those seven fields exist only after a **commit**, and a commit is the
prepared handoff. So this spike does need throwaway switching code, and §5's
"do not implement the prepared handoff" means something narrower than it
sounds:

> Write the smallest harness that primes a successor and swaps to it at a
> chosen film boundary. Do not build the transaction — no `action_id`, no
> reserve/prime/commit phases, no server involvement, no branch on `main`.
> The harness exists to produce seven numbers and is then thrown away.

State in §6 how the harness's switch differs from M6's, because a runway
measured against a switch M6 will not use is a number that will be wrong in a
way nobody can see later.

**`scripts/playback-lab` does no dual-pipeline preparation.** It is worth
using for what it does do — an isolated server, a real browser, a fixture
corpus, a network shaper, and a physical-Apple runner — but it will not
measure the thing this spike is about.

### 3.2 Web — hls.js, second detached pipeline

**Dual proof:** a second `MediaSource` and `<video>` buffer the successor
without destroying the current MSE/video and without exceeding the browser's
memory or decoder limits.

```bash
make playback-doctor              # verify browsers, drivers, codecs, filters
make playback-fixtures            # build the fixture corpus once
make playback-smoke               # Chrome, unshaped
make playback-smoke-safari        # Safari matters most
```

Those establish the rig; none of them shapes the link. Network duplication is
measured on a **stable** contended link with two pipelines pulling, so pass an
explicit steady profile to `scripts/playback-lab run --network-profile …`
rather than reaching for the named `8mbps-to-1.5mbps` descent, which is a
bandwidth-cliff recovery rig for a different acceptance and is only applied at
all by suites that require it.

Safari matters most because it is the platform most likely to refuse a second
pipeline.

**Fallback if dual preparation does not hold:** server-prime, then a measured
single-player replace.

### 3.3 Apple — AVPlayer, successor item

**Dual proof:** a successor `AVPlayerItem` acquires playable buffer while the
current item renders, inside tvOS/iOS resource limits.

Read buffer per §2.2 and §2.4 — **not** `isPlaybackLikelyToKeepUp`, and
**not** `status == .readyToPlay`.

Run on real hardware. The simulator's decoder allocation is not the device's,
and this measurement is entirely about decoder allocation.
`scripts/playback-lab device-run --device UDID …` already launches, shapes,
observes and restores one physical Apple device, and its probe reports film
position, contiguous runway, buffer flags, access-log throughput and session
identity — most of §3's table for the *predecessor*. It cannot prime a
successor; that is §3.1's harness.

Cover at least one Apple TV and one iPhone — the Apple TV because it is where
the 2160p pressure is, the iPhone because it is where the memory ceiling is.
There is no named Apple roster in the ansible inventory
(`mobile_release_required_apple_devices: []`, minimum 1), so **record the
devices you actually used, by name, from `xcrun devicectl list devices`**, or
the Apple rows in §6 cannot be attributed to hardware.

**Fallback:** `AVQueuePlayer` or single-item replace, with an honest
interruption.

### 3.4 Apple has no first-frame signal — decide how you will get one

Android has `onRenderedFirstFrame()` (`Controller.kt:469`) and web has
`requestVideoFrameCallback`. Apple has neither: there is no
`isReadyForDisplay`, no `AVPlayerItemVideoOutput`, and no TTFF event anywhere
in `clients/apple/Sources/`.

`timeControlStatus == .playing` fires when the *clock* starts, not when a
frame is presented, and on a codec or dynamic-range change that gap is
precisely the interval being measured. Use `AVPlayerLayer.isReadyForDisplay`
or an `AVPlayerItemVideoOutput` polled for `hasNewPixelBuffer`, and say in §6
which. A clock-start timestamp recorded as first-frame latency flatters the
codec-change case, which is the case the fallback decision turns on.

### 3.5 Android — Media3, second player or preload manager

**Dual proof:** a second `ExoPlayer` (or the preload manager) buffers on the
target hardware without decoder starvation.

Read the successor's buffered position directly per §2.2. `Player.STATE_READY`
is the Android member of the same family as §3.3's and carries the same
warning.

**Tunneled decoding is on for televisions and off for phones**, and the client
decides that itself:

```kotlin
// clients/android/.../Controller.kt:1299-1303
// Tunneled playback hands decode and A/V sync to the TV SoC's own
// pipeline, which is what 4K HDR on a Shield or a Chromecast is built
// around. Requested only on television devices: on a phone it buys
// nothing and some handset decoders refuse the mode outright.
.setTunnelingEnabled(isTelevision(context))
```

Tunneling is the single most likely reason a second `ExoPlayer` is refused on
a TV. Measure with tunneling set the way the shipped client sets it for that
device, and record which — a dual-player result with tunneling off is a
measurement of a configuration the fleet does not run.

The named hardware is the deployment roster in the ansible inventory: **Pixel
11 Pro XL · Motorola razr ultra 2025 · Xiaomi 25019PNF3C**. The **TCL 9445X**
is *not* in that inventory — it is in the `mobile_release` role defaults
alongside `Pixel 10 Pro Fold`, a Lenovo tablet (`TB322FC`) and `Xiaomi 15
Ultra`, and the inventory mentions it only in a comment saying it is paired
but offline and therefore known-but-optional. Any of those four may be
attached when this runs; include whatever is.

**Determine, do not assume, whether the TCL is a television**, because that
single fact decides both its priority here and whether tunneling applies:
`isTelevision(context)` is the client's own test. If it is a TV it is the most
informative device in the fleet — least decoder headroom, so plan §5.3's
one-encoder-slot case is its normal state rather than its edge case, which is
also roadmap §8's open question 4.

**Fallback:** single-player media-item replace, with an honest interruption.

## 4. What a failure means — and what it does not

**Unsupported dual preparation does not block the protocol.** It selects that
platform's measured fallback, sets `dual_player_preparation` to a *measured*
`false` rather than the placeholder one (§1), and does one more thing:

> It prevents the UI from calling that path seamless.

Plan §5.2 already draws this line — *a measured display-mode blink is reported
honestly rather than hidden under that term*. Writing "seamless" over a path
with a visible interruption is a product lie, and one that costs support time
later: the viewer reports a bug against a feature whose own copy says it
cannot happen.

## 5. Non-goals

- **Do not build the transaction.** §3.1 says exactly how much switching code
  is permitted and that it is thrown away. No `action_id`, no phases, no
  server involvement, no branch on `main`.
- **Do not run this on simulators or emulators.** A measurement of decoder
  allocation on a simulator is a measurement of a Mac.
- **Do not average across platforms.** Three numbers, three fallbacks. A
  single runway that satisfies all three is a runway that is wrong twice.
- **Do not land a capability change server-side alone.** Correcting
  `dual_player_preparation` is a coordinated client release —
  `scripts/ship-physical` or the Ansible `mobile-physical.yml` path — and the
  fleet gate in
  [M5-CLIENT-ACTION-OWNERSHIP-HANDOFF.md](M5-CLIENT-ACTION-OWNERSHIP-HANDOFF.md)
  §5 applies to it.

## 7. Two questions this spike also answers

Both are open in roadmap §8, both shape M6's structure rather than its
details, and neither can be answered from a Linux box:

1. **Is a bounded admission overcommit proven safe on any of the fleet's
   hardware?** Plan §5.3's first fallback assumes one exists. If none does,
   the one-encoder-slot path is M6's common case rather than its exception,
   and M6's shape changes accordingly. The TCL is the likeliest place to find
   out, if §3.5 establishes it is a television.
2. **What interruption bound is acceptable for
   `buffered_break_before_make`?** Its acceptance criterion is "within its
   measured interruption bound", and nobody has measured or chosen one. §3's
   `first_frame_ready` latency on the fallback path is that measurement — which
   is why §3.4 matters: on Apple that number does not exist yet.
