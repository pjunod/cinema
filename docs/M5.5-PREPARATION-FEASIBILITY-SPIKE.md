## 1. Why this exists, and what happens if it is skipped

M6 builds a prepared handoff: a successor stream is primed while the current
one still plays, and the switch commits only once the successor says it is
ready. **"Ready" is a promise the client makes to the server**, and the wire
that carries it is frozen at the end of this spike. Every milestone after M6
is built on that wire.

So the failure this spike exists to prevent is specific:

> A player reporting "ready" while holding no successor buffer produces a
> commit that stalls at the switch boundary — the exact failure prepared
> handoff exists to prevent.

**An asset-metadata callback or an `AVPlayer` / `Media3` ready state is not
`buffer_ready`.** Both mean "I could start"; neither means "I have contiguous
film through the boundary." If the contract is frozen from what those APIs
say rather than from what the hardware does, every client will honestly report
ready and every commit will stutter, and the wire will make that
indistinguishable from a bug.

This is a **measurement** milestone. It produces numbers and one decision per
platform. It does not produce a branch.

## 2. What is being measured

Three acknowledgements, defined so that they mean the same thing on three
platforms that agree about almost nothing:

| ack | means | measured how |
|---|---|---|
| `metadata_ready` | the successor's manifest/item is parsed and its decoder eligibility accepted | timestamp of the platform's parse/eligibility callback |
| `buffer_ready` | the successor holds **contiguous film time through the switch boundary, plus its measured safety runway** | the platform's own buffered-range query, read at the boundary — never a ready flag |
| `first_frame_ready` | observed **only after commit**, with wall latency and film position | first presented frame of the successor |

`buffer_ready` is the whole spike. The other two are cheap.

### 2.1 The safety runway

The runway is not a constant to be chosen — it is measured here and becomes
part of the contract. It is the answer to: *after the successor claims
contiguous film through the boundary, how much more does it need so that the
commit does not stall?* Measure it as the smallest runway at which twenty
consecutive commits produce zero stall, then state it per platform.

## 3. The procedure, per platform

Run each platform's §3.x twice: once **same-codec, same grade** (a
resolution/bitrate change only — the axis §5.2 expects to be genuinely
transparent), and once **codec or dynamic-range change**. The second run is
expected to be worse; the point is to know by how much.

For every run record, per attempt:

| field | unit | why it is here |
|---|---|---|
| peak memory | MB | dual pipelines double the buffer pool; phones kill apps for this |
| decoder instances | count | the one-slot problem in §5.3 is decided by this number |
| network duplication | Mbit over the prime window | two streams on one link is why a prepared handoff can cause the stall it prevents |
| old-stream continuity | stalls observed in the predecessor | **the predecessor must not suffer for the successor** |
| buffered-through at ack | ms of film past the boundary | the claim being validated |
| switch position error | ms | film time skipped or repeated at the boundary |
| first-frame latency | ms after commit | what the viewer sees |

### 3.1 Web — hls.js, second detached pipeline

**Dual proof:** a second `MediaSource` and `<video>` buffer the successor
without destroying the current MSE/video and without exceeding the browser's
memory or decoder limits.

Use `scripts/playback-lab`, which already drives the real player through
Chrome/Edge DevTools and Safari/Firefox WebDriver and already owns a network
shaper. Its `8mbps-to-1.5mbps` profile is the descent this spike needs.

```bash
make playback-lab-doctor          # confirm the browsers and drivers are present
scripts/playback-lab fixtures     # build the fixture media once
scripts/playback-lab run --suite smoke                    # Chrome
scripts/playback-lab run --suite smoke --browser safari   # Safari matters most
```

Safari matters most because it is the platform most likely to refuse a second
pipeline, and it is the one an Apple TV browser shares lineage with.

**Fallback if dual preparation does not hold:** server-prime, then a measured
single-player replace.

### 3.2 Apple — AVPlayer, successor item

**Dual proof:** a successor `AVPlayerItem` acquires playable buffer while the
current item renders, inside tvOS/iOS resource limits.

Read `loadedTimeRanges` on the successor item — **not**
`isPlaybackLikelyToKeepUp`, and **not** `status == .readyToPlay`. Those are the
two APIs this spike exists to distrust.

Run on real hardware, not the simulator: the simulator's decoder allocation is
not the device's, and this measurement is entirely about decoder allocation.
Cover at least one Apple TV and one iPhone — the Apple TV because it is where
the 2160p pressure is, the iPhone because it is where the memory ceiling is.

**Fallback:** `AVQueuePlayer` or single-item replace, with an honest
interruption.

### 3.3 Android — Media3, second player or preload manager

**Dual proof:** a second `ExoPlayer` (or the preload manager) buffers on the
target hardware without decoder starvation.

Read the successor's buffered position directly. `Player.STATE_READY` is the
Android member of the same family of APIs as §3.2's, and carries the same
warning.

The named hardware is the deployment roster in the ansible inventory: **Pixel
11 Pro XL · Motorola razr ultra 2025 · Xiaomi 25019PNF3C**, plus the TCL 9445X
when it is online. The TCL is the one that matters most and the one most
likely to fail: an Android TV box has the least decoder headroom in the fleet,
and §5.3's one-encoder-slot case is its normal state rather than its edge case.

**Fallback:** single-player media-item replace, with an honest interruption.

## 4. What a failure means — and what it does not

**Unsupported dual preparation does not block the protocol.** It selects that
platform's measured fallback, and it does one more thing:

> It prevents the UI from calling that path seamless.

§5.2 already draws this line — *a measured display-mode blink is reported
honestly rather than hidden under that term*. Writing "seamless" over a path
with a visible interruption is a product lie, and it is a lie that costs
support time later, because the viewer reports a bug against a feature whose
own copy says it cannot happen.

So a platform that fails the dual proof produces two artifacts: its fallback,
and the interruption bound that fallback is held to.

## 5. Non-goals

- **Do not implement the prepared handoff.** M6 does that, and it is not
  allowed to start until §6 below is filled in.
- **Do not choose the acknowledgement field names here.** Name them from the
  measurements, in M6, so a field cannot outlive the thing it described.
- **Do not run this on simulators or emulators.** A measurement of decoder
  allocation on a simulator is a measurement of a Mac.
- **Do not average across platforms.** Three numbers, three fallbacks. A
  single runway that satisfies all three is a runway that is wrong twice.

## 7. Two questions this spike also answers

Both are open in
[REMAINING-ROADMAP-HANDOFF.md](REMAINING-ROADMAP-HANDOFF.md) §8, both shape
M6's structure rather than its details, and neither can be answered from a
Linux box:

1. **Is a bounded admission overcommit proven safe on any of the fleet's
   hardware?** §5.3's first fallback assumes one exists. If none does, the
   one-encoder-slot path is M6's common case rather than its exception, and
   M6's shape changes accordingly. The TCL is the likeliest place to find out.
2. **What interruption bound is acceptable for
   `buffered_break_before_make`?** Its acceptance criterion is "within its
   measured interruption bound", and nobody has measured or chosen one. §3's
   `first_frame_ready` latency on the fallback path is that measurement.
