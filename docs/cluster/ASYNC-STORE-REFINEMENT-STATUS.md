## 1. Implementation — source-derived control and durable transitions

Production library workers consume the shared `plurx-worker-control::library_driver` interpreter through a thin Tokio environment adapter. One owned work future retains its publisher and domain reference through interruption; cancellation precedes joining that same future, then publisher drop, local domain release attempt, queue settlement/retirement and physical admission drop. The source binding now includes the shared retry policy, driver settlement getter and daemon adapter guards. The shared selector polls queue loss, domain loss, work, then pressure ticks. A ready tick cannot hide a ready work result; no concrete Tokio starvation incident is claimed from a coarse polling schedule.

Driver inventory invokes actual `drive`: 48 reachable control states, 52 accepted edges and 572 explicit rejections across 13 reply classes. Those are inventory counts, not temporal acceptance. Control takes reply tags without numeric payloads; tag independence of the lifecycle guards is a reviewed composition lemma, not a new all-integer machine proof. Runtime assertions and representative arithmetic tests cannot replace that lemma or the existing arithmetic proof.

The Store harness calls actual validated methods, SQL, migrations and triggers. Its savepoint/replay machinery checks full-row identity, rollback, operation preimages and independent invariants. Source, compiled migrations and installed schema are bound. The replacement product oracle must preserve these checks, including refused-operation full-preimage equality and logical-resolution read-only behavior. At the previous pushed candidate, 16 core cases and 34 Rust commands were defined, including backend history, 124 predicate rows, three retirement conformance cases and the existing cancellation-revision case. The replacement registry is being integrated; these counts are historical, not a frozen acceptance total. The backend history and remaining Store cases have not run. The sampled history requires completed markers for memory SQLite, file SQLite and real three-voter Hiqlite; its fault deliberately discards an applied acknowledgement and is not a real transport-timeout injection.

## 2. Domain — exact concrete bounded input protocol

Domain D contains two selected jobs with paired requests/waiters, one shared root, two nodes with one physical permit each, and a foreign domain holder. There are at most two successful claims per job, one renewal per claim and one domain acquisition per owner. Four selected attempt identities and two mismatch identities are distinct. Allocator exhaustion is outside D because the attempt budget is reached first. There are no demand re-arrivals. Persistent lost-claim keys `(job,node,selected claim_id)` permit at most eight recovery episodes across Idle/recycle. Actual resolution/reread/cancel and 250 ms retry wakes retain the original 30-second local deadline; timer service is an explicit fairness premise. This is a finite fault-input assumption, not a production limit.

All integers remain concrete. Raw generated job IDs stay bound in product identity; clocks retain exact wall and monotonic anchors without a numeric quotient or fixed horizon. Ordinary settlement uses a saved token actually captured under the local mutex, including a historical revision; the SQL outcome determines acceptance. Captured Yield/Retry deadlines, immutable failed-attempt retry inputs, local guards, request time, validation outcomes and future eligibility are represented. Every input restriction and cutoff is explicit. D defines eligible primitive inputs; the closure claim covers all demands of the exact selected two-worker composition, including capacity-only queries, rather than every D input at every arbitrary Store state. A global 20,000 distinct Store identity cap aborts without a complete receipt. Independent numeric preflight must also show that every TLA-consumed value and candidate arithmetic intermediate fits pinned TLC while preserving source arithmetic. Unsupported numbers fail qualification globally without clipping timestamps or excluding inputs.

The coordinator selected this narrower domain because first-appearance/rank normalization has no demonstrated preservation argument for increment, MAX, stale identities and clock gaps. Generated SQL tables are source-derived semantics, not independent oracles for themselves. Catalogue item publication remains an opaque operation/conformance boundary.

## 3. Fairness — separate cleanup from selected success

[The exact contract](../../verification/async-driver-refinement/CONTRACT.md) defines these conditional checks:

| Claim if qualification succeeds | Required boundary |
|---|---|
| Finite product safety | Actual driver/SQL outcomes, independently complete candidate/demand/successor coverage, amended `Next`, explicit environment and independent raw-row/transition assertions |
| Attempt cleanup | `[]WithinEpisodeCapacity => AttemptCleanup`; matching SQL inputs remain available, with named runtime dispatch/application/reply/return and work/join return fairness |
| Both fixed requests complete | Stable node/job pairing, lease-window-bounded wall/monotonic service, queued eligibility progress, recurring physical opportunity, strongly fair admission and a separate durable claim-win premise; available successful operations/work before budgets or leases are exhausted |
| Nonvacuity | A reachable witness with both durable requests freshly done and both local physical admissions dropped |

Selected success still permits an applied completion acknowledgement to be lost and mapped to `WorkFailed`. The retained captured token admits a refused `SettleRetry` self-edge after durable completion; that branch is present in the actual Store graph and does not itself create a missing-edge cleanup exemption.

`GuardBeforeRevoke` is a structural consistency check of the modeled ordering, not independent evidence about adapter lock service. Task fairness alone does not prove branch polling, mutex service, backend return or child termination. Arbitrarily persistent fair errors do not imply successful work. Stable-success permits time steps only inside explicit live lease/deadline windows and excludes owner removal and foreign acquisition; finite demand cannot establish infinitely many fresh completions. Safety retains cutoff states even where conditional cleanup does not apply.

The clean stable contexts may never reach delayed incomplete queued work. The independent base-certificate `eligibility_mechanics_witness` is a separate required existential check: an actual accepted ordinary Yield/Retry preserves the same incomplete queued job/deadline through exact, all-worker-safe wall steps until eligibility, with a claim attempt remaining. It does not establish stable fairness nonvacuity or fair recovery from arbitrary failed histories.

`NoTwoSourceReaders` counts durable records with state running and queue expiry after the sampled time; it does not bound physical readers while expired work awaits cancellation or join. A local queue handle can outlive atomic last-request retirement. Local admission drop or domain release does not establish durable expiry, quiescence or rollback of a committed call.

## 4. Residual assumptions — this is not a complete Rust simulation proof

The finite relation does not discharge Tokio/OS scheduling, lock service, child/process return, filesystem behavior, SQLite atomicity/visibility or Raft/Hiqlite internals. Inner retirement and renewal-resolution interleavings, non-ordinary error classifiers and publication-lock granularity remain reviewed or conformance contracts. Ordinary payload capture, request/application samples and local guard outcomes belong to the selected finite clock/input domain; arbitrary clock histories remain outside it. Full-row state hashes depend on the Rust producer/replay checks; compact projections cannot independently reconstruct hidden rows. These boundaries must remain in receipts and any result summary.

Current Hiqlite insertion retries allocator-identity conflicts at most four times; a lost-reply timeout does not take that retry branch. The three publication clock samples and backend time-check differences remain outside this common-SQL graph's publication boundary. Local revocation after commit is not evidence that the durable call rolled back.
