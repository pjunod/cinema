## 1. The only human step, and it happens once

The previous attempt at this measurement produced nothing, and not for a
technical reason: every iOS device and the Apple TV refused a foreground
launch and the Pixel sat on the keyguard. `scripts/ship-physical` has no
wake or unlock handling — grep it; there is none — and a passcode cannot be
entered over `devicectl`.

So before you start, Paul (or anyone at the desk) does this once, per device:

| device | action |
|---|---|
| each iPhone | unlock · Settings → Display & Brightness → **Auto-Lock → Never** · leave on charge |
| Apple TV | wake · Settings → General → **Sleep After → Never** |
| each Android | unlock · leave on charge (you will hold it awake yourself, below) |

Then you keep them awake, which you *can* do:

```bash
adb -s <serial> shell svc power stayon usb    # screen stays on while charging
adb -s <serial> shell input keyevent 82       # dismiss a swipe-only keyguard
```

There is no `adb` equivalent for Apple. If an Apple device has re-locked
mid-run, `xcrun devicectl device process launch` fails and **that is the
signal** — record it against that device and carry on, per §2.

Restore `Auto-Lock` and `Sleep After` when you are finished. Note in your
output that you did.

## 3. Order of work

**Web first, then Android, then Apple.** Not the spike's section order — this
is cheapest-signal-first, and each stage de-risks the next.

1. **Web** needs no device and no signing. It is where you debug the harness
   logic and the buffer readers with a fast loop. Safari matters most
   (spike §3.2) because it is the platform most likely to refuse a second
   pipeline.
2. **Android** is fully scriptable over `adb`, so it is where you validate
   that the harness works on a real device.
3. **Apple** last, because it is the most expensive to iterate and it is the
   one with an unsolved problem — spike §3.4, there is no first-frame signal
   and you have to choose one.

## 4. What exists, and what you have to write

**Use, do not rebuild:**

```bash
make playback-doctor              # verify browsers, drivers, codecs, filters
make playback-fixtures            # build the fixture corpus once
make playback-smoke               # Chrome, unshaped
make playback-smoke-safari        # Safari
scripts/playback-lab device-run --device UDID --target URL --public-host HOST \
    --file-id ID --network-profile PROFILE [--observe SECONDS] [--json PATH]
```

`device-run` launches, shapes, observes and restores one physical Apple device
and reports film position, contiguous runway, buffer flags, access-log
throughput and session identity — **most of §3's table, for the predecessor**.
It cannot prime a successor.

**Priming the successor is the harness you write** (spike §3.1): the smallest
thing that primes a second pipeline and swaps to it at a chosen film boundary.
No `action_id`, no reserve/prime/commit phases, no server involvement, no
branch on `main`. It exists to produce seven numbers and is then deleted.

**Do not shape the link with the named `8mbps-to-1.5mbps` profile.** That is a
bandwidth-cliff recovery rig for a different acceptance. Network duplication
is measured on a *stable* contended link — pass an explicit steady profile to
`--network-profile`.

**Do not run any of this on a simulator or emulator.** A measurement of
decoder allocation on a simulator is a measurement of a Mac.

## 5. The three traps that will silently produce wrong numbers

These are the ones worth restating, because each yields a plausible number
that is not the number:

1. **A ready flag is not `buffer_ready`.** `isPlaybackLikelyToKeepUp`,
   `status == .readyToPlay`, `Player.STATE_READY` all mean *I could start* —
   not *I hold contiguous film through the boundary*. All three clients already
   map exactly those flags for a different question, which is what makes them
   the trap. Use the readers in spike §2.2, and apply the contiguity rule.
2. **Every buffered-through number needs its origin offset** (spike §2.3).
   Player time is not film time. A runway recorded without the offset is wrong
   by the offset and looks fine.
3. **Apple's clock-start is not its first frame** (spike §3.4).
   `timeControlStatus == .playing` fires when the clock starts. On a codec or
   dynamic-range change the gap between that and a presented frame *is the
   interval being measured*, so a clock-start timestamp flatters exactly the
   case the fallback decision turns on. Use `AVPlayerLayer.isReadyForDisplay`
   or an `AVPlayerItemVideoOutput` polled for `hasNewPixelBuffer`, and say
   which you used.

## 6. Two runs per platform, seven numbers each

Per spike §3: once **same-codec, same grade** (resolution/bitrate only — the
axis expected to be genuinely transparent), once **codec or dynamic-range
change** (expected worse; the point is to know by how much).

Record per attempt: peak memory (MB) · decoder instances (count) · network
duplication (Mbit over the prime window) · **old-stream continuity** (stalls in
the *predecessor* — it must not suffer for the successor) · buffered-through at
ack (ms past boundary, with origin offset) · switch position error (ms) ·
first-frame latency (ms after commit).
