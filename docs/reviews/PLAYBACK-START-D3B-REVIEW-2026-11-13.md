## Blockers

### B1 — a stale ingress plan fails every negotiated create, and nothing closes the view
`crates/plurxd/src/http/hls/create.rs:3360-3367` plans from the view and captures that plan's binding (`capture_create_planning_binding`). The catalog is still D3d's: `media_pool.rs:1469-1479` hands the captured binding to `local_quality_catalog`, which reads the snapshot **by quorum** (`media_pool.rs:1996-2001`) and answers `CatalogCause::StaleSource` when it differs (`:2006-2010`); peers are sent the same `expected_binding` (`:1495-1515`) and do the same. `create.rs:2349-2360` turns an incomplete catalogue into `503 quality_catalog_unavailable`.

Before D3b both reads were quorum reads, so they differed only if something changed between them. Now the first is the replica. Scenario: any `playback.*`/`transcode.*`/extra-key save, a rescan of this file, or a dv-title publish (it rewrites `files.probe_json`, which the binding digests) commits from another node; this ingress holds a valid proof but has not applied it (the case E1's floor section names). Every caps-v2 create for the file on this node now answers 503, and so does each client retry (1 s / 2 s / 4 s), until the replica applies — because `close_after_refusal` is called only from the `RemoteStartFailure::PlanChanged` arm (`create.rs:4448`). The quorum fact that the view is stale is in hand at `media_pool.rs:2009` and is dropped. This is §5's "ingress replica behind" row, a behaviour change the brief excludes, and it sits before any owner is asked, so the built refusal path never sees it.

**Fix:** when the catalogue reports `StaleSource` and `start_plan.source == ViewSource::View`, call `close_after_refusal`. Better, and cheap here because nothing durable exists yet (the catalog runs inside `resolve_plan`, before the claim): re-plan once from Authority (`planning_from_authority`), re-capture the binding and run the catalog once more. That is §4.3's "one re-plan per request" at the point where it costs nothing, and it removes record decision 3's reason for skipping it. Add the held-apply stale-ingress test §8 asks for; it fails on this head.

## Should fix

### S1 — after `PlanChanged` the refuted plan is offered to the next candidate, including this node
`create.rs:4440-4458`, then the loop at `:4460-4487` (`Err(error) => last_error = Some(error)` and continue). An owner has just proved at Authority that binding *b* is superseded. The next candidate is offered the same `Arc<StartPlan>`; if it is this node, `validate_candidate_planning_binding` (`transcode/manager/create.rs:766-773`) compares the request's binding with the plan's own and passes, where `f74752606` read Authority and refused ("never authorizes stale execution", `transcode/manager/create.rs:994-999`). The session is one revision, so it is not mixed, but it is built on a revision this process knows is dead. Contract §4.3 says re-plan before the next candidate.
**Fix:** `break` out of the candidate loop on `PlanChanged` and answer the typed 503 (or do B1's re-plan here too once the claim can carry it).

### S2 — an unbound remote start can mix the ingress's view revision with the owner's Authority revision
`internal_media_sessions.rs:203-211`: `expected` is `candidate_catalog.binding`, present only on a candidate route. For any other create with a remote owner (`start_plan.rs:119-124`, `Unbound`) the owner plans from Authority and compares nothing, while the ingress derived `typeless_playlist` (`create.rs:4174-4177`), placement and the request from its view plan. On `f74752606` that window was the gap between two quorum reads; now it is the ingress's replica lag. A wrong recorded `typeless_playlist` outlives the start (takeover reads it).
**Fix (no wire change):** plan from Authority at the ingress when the request will carry no binding and the chosen owner is remote; or state in the record that §4.4 holds on bound routes only, and count it (the Developer row already has `unbound`).

### S3 — the refusal path and two of §8's floor cases have no behavioural test
- Nothing tests `remote_start_plan_changed` (`media_sessions.rs:1991`), the 409 body (`internal_media_sessions.rs:69-75`), the `PlanChanged` arm or its floor close. `start_plan_tests.rs::a_setting_saved_before_the_owner_starts_refuses_rather_than_mixing` calls `close_after_refusal` by hand on SQLite, where every floor is always met: its "re-plan sees the new value" assertion passes with the call deleted; only the counter is checked.
- §8 "files floor" requires a `dv_title_jobs` trigger write and a probe result through `background_job_commands` to close the view on the writing node. Both are classifier-only (`applied_view.rs:1700`); the replica test (`store_contract/applied_view.rs`) drives a settings save, `upsert_file` and `delete_library`.
- No commit carries a `Regression-Test:` trailer, and neither record states a counterfactual run ("Results are in the report to the coordinator"). §8 asks each PR to record it.
**Fix:** one media-sessions test for the 409 body → `PlanChanged`; one ingress test asserting `ViewFallback::Floor` on the next plan after a refused remote start (cluster-read-cost-validation); add the two writers to the replica test; add the trailers.

### S4 — the owner's planning read left the start's stage deadline
`internal_media_sessions.rs:203-211`. On `f74752606` the owner's snapshot read ran inside `restore_catalog_context` under `restore_deadline = deadline.min(create_stage_deadline(2 s))` (`candidates.rs:1616-1618`). `owner_plan` runs before it with no deadline: up to two quorum reads at the store's own 3 s timeout each, before placement is even checked, while the ingress is waiting on `placement_deadline`.
**Fix:** `tokio::time::timeout_at(start_deadline.min(create_stage_deadline(2 s)), owner_plan(..))`, a timeout answering 503.

## Notes

- **N1 — Developer row arithmetic.** `developer.rs:1233`: an owner mismatch counts one view read and one `binding_mismatch` authority read for one plan, so "N of M plans" over-counts plans; SQLite counts the store as "view". The G1 per-shape counts are absent (declared).
- **N2 — a plan's limits become process-wide.** `transcode/manager/start.rs:121-128` (`ahead_limits_for_start`, callers `:1106`, `:2150`) publishes the start's settings as the snapshot every session is held to for 2 s. Those settings used to be a fresh quorum read; with a plan they are as old as the plan. Bounded and small, but it is the one place a plan's values leave their own session.
- **N3 — `queue_sql` label.** The task-local cannot leak: `LocalKey::scope` binds to the wrapped future, a spawned task falls back to `queue_sql` (under-labels, never mislabels), nested scopes resolve to the inner Store method. But `queue_sql` is still emitted for every other queue statement and was removed from `NOT_A_STORE_METHOD` (`consistent_read_census.rs:586-594`) because no call site spells it — the census's claim that every emitted label is a Store method or listed is no longer true. List it with that reason.
- **N4 — what the pin does not see.** The after-table has no `playback_planning_snapshot` row in any shape, so none of the five shapes counts the catalog's quorum snapshot (`media_pool.rs:1998`): B1's path is outside the pin, and "the one planning-input read left" (record §10) is true only of these shapes. The rolling shape is 20 **or 23** (`cluster_activity.rs:2355-2361`, pre-existing tolerance); the record should say so.
- **N5 — census reach.** `every_files_writer_is_floored_or_writes_no_replicated_row` (`applied_view.rs:2277`) exempts all of `plurx-core/store/` by prefix, so it cannot catch a raw-client files writer added there; it leans on the `TimedClient` census. `deletes_rows_of` (`replicated.rs:1236`) does not see `UPDATE OR REPLACE` (none in tree today).
- **N6 — paperwork.** `b538e141f` cites record "§9–12"; the record has §9–10 plus a separate file. The new 503 is `ApiError::typed` with no `Retry-After`, where `media_owner_transition` carried one; all three clients retry `quality_catalog_unavailable` on their own ladder, so no client change is needed.

- **Chains.** Takeover, resurrection, the prepared successor, processed upgrade and its qualification, the compatibility preview, `plan_preparation_with_candidate` and `live_tv_worker` pass `None`. Each planned helper's `Some` branch parses as its `None` branch does (`remote_placement_ready`, `cluster_playlist_is_typeless`, `software_budget_planned`, the live-recovery switch, `vod_settings_from`'s eleven keys are all in the list).

An old ingress reads the new 409 as it read the bodiless one; a new ingress reads an old owner's bare 409 as transport, as before. `note_fact` raises both floors and they reopen on the next applied confirmation.
- **Formal rebind (`b538e141f`).** 17 rows as stated (durable-jobs 13, operation-progress 4; hash counts match 11 + 5 + 1). The described hunks are the hunks: guard rename in `hiqlite.rs`, label-only wrappers in `background_jobs.rs`, the label variable in `hiqlite_background_jobs.rs`. Honest.
- **The refusal deviation** (no same-request re-plan after an owner's 409) is acceptable **after the claim**, with S1's `break`. It is not acceptable as the only stale-ingress recovery, because the stale case is caught before the claim (B1).
