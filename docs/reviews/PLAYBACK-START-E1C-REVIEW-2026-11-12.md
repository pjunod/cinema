Short paths: `ms.rs` = `crates/plurxd/src/media_sessions.rs`; `av.rs` = `crates/plurx-core/src/store/applied_view.rs`; `rvt.rs` = `crates/plurxd/src/media_sessions/route_view_tests.rs`; `inv.rs` = `crates/plurxd/src/http/applied_route_inventory.rs`; `http/` = `crates/plurxd/src/http/`. ## What holds (checked, no finding)

- **Fences stay on quorum.** `authoritative_route_resolution_at` (`ms.rs:2838-2873`), `control_route` (`ms.rs:3092`), `authorize_prepared_media_before` (`ms.rs:2930-2978`), `status_media_route_resolution_before` (`ms.rs:2893-2913`) read `self.store` only. `self.applied` is touched at seven places, all inside `raw_route_before`, `cached_route`, `insert_cached_route` and `observed_now` (`ms.rs:3047, 3082, 3487-3495, 3599, 3616-3617`). `by_incarnation`, `for_playback`, the staged read, the takeover switch read and `serving_fence.rs` are untouched by the diff.
- **`status.rs:39`.** Only `ActiveLocal`/`ActiveRemote` skip the confirming quorum read (`http/hls/status.rs:43-61`). `ActiveLocal` never answers alone: the `StatusBracket` read (`:74-93`) is still a quorum read and `same_route_authority` compares the view's route against it, so a stale admitted route fails closed as a retryable transition. A stale `ActiveRemote` is relayed; the old owner answers 404/409/410 and `StatusReclassify` (`:161-170`) decides.
- **The per-row floor (the builder's deviation) is sound in principle.** `observe()` (`av.rs:784`) takes the instant after the acknowledgement at every publication (`ms.rs:3445, 3536`) and after the quorum read returns (`ms.rs:3043, 3063`); `floor_met` (`av.rs:814-826`) requires an even generation, a held proof and `confirmed_since(fact) <= applied_index`, and `confirmed_since` takes the *minimum* index among confirmations started after the fact (`mig.rs:6405-6420`). Replacement of one `Observed` by a newer `Observed` is safe (the later fact subsumes the earlier). Restart is safe (a proof after restart needs an applied confirmation started after start). What is not safe is finding B1: one drop that does not hold the floor.
- **Single flight.** Retire and replace happen only in the second `cached_route` call under `route_queries[shard]` (`ms.rs:3013-3027`); a publication racing a lookup bumps the generation or leaves an `Observed` entry, and `cache_queried_route_result` defers to either (`ms.rs:3557-3569`).
- **Legacy layout answers Authority** (`av.rs:1081-1083`), and a process that has seen layout 2 through Authority while its own replica is still legacy gets a SQL error on `owner_key` (`hiqlite_sessions.rs:347-351`), i.e. `LocalError` → Authority. `validation_assume_installed_session_layout` is behind `cluster-read-cost-validation`, which `crates/plurxd/Cargo.toml:52` does not enable, and has one caller, a store-contract test.
- **No gate, no switch, no new task or timer.** `cluster.bounded_replica_reads` is not consulted; the Developer row computes at read time and blocks nothing; metric label sets are fixed arrays (9 sites × 2 sources, 5 lookup results).
- **Eviction is O(n) only when full** (`ms.rs:3592`), and `plurx_media_session_route_prune_entries` records that scan.

## Blockers

### B1. An unretired `Observed` entry is removed before the quorum read that replaces it; if that read does not land, a lagging replica revives the pre-release row
- **Contract:** §4.4 — "A view read never replaces an unretired `Observed` entry, whatever the slot does." Record §3 — `hold_floor` "closes the table only when it must drop an unretired entry (eviction), so dropping an entry never lets a lagging replica answer that row."
- **Evidence:** `cached_route(.., exclusive = true)` on an entry past its lease with the floor unmet does `routes.remove(session_id)` and returns `Quorum` (`ms.rs:3499-3505`). No `hold_floor`. The quorum read follows at `ms.rs:3035-3043`, three awaits later. The entry is then gone for good if (a) the read returns an error or hits `deadline` (`.map_err(lookup_timeout)??`, `:3041`); (b) the request future is dropped — a player aborting a segment GET does exactly that — at `wait`/`read`/`lock_routes`; or (c) the generation shard moved meanwhile, where `cache_queried_route_result` returns "whatever the cache holds", now nothing, i.e. `Absent`, and inserts nothing (`ms.rs:3557-3564`).
- **Failure:** node F releases session S (tombstone `Observed` at `t`). F's replica is behind the release and F holds a proof anchored on a confirmation that *started before* `t` and is still inside its lease — apply lag between one sampling period and the lease, or one slow watermark sample (750 ms timeout), is enough. At `t + 1 s` a lookup removes the tombstone and starts the quorum read; the client disconnects (or the leader is slow and the deadline fires). The next lookup finds no entry, reads the view, and `admit` passes: the table floor was never raised (`av.rs:866`, `floors.get(table)` is `None`). F's replica answers S **active, owned by F**, cached as `View` under a current stamp. `relay_if_remote` returns `Ok(None)` for `ActiveLocal` (`http/hls/relay.rs:26`) and the request falls through to the local actor the tombstone exists to shield (`ms.rs:3459-3462`). The old cache could not do this: its tombstone was replaced only by a completed quorum read.
- **Fix:** do not remove at `:3503`. Leave the entry in place and let the quorum answer replace it on success — in `cache_queried_route_result`, an `Observed` origin produced under the shard may replace an `Observed` entry; a `View` origin still may not. (Calling `hold_floor(fact)` at `:3503` also closes the hole but sends every session to quorum for a sampling period each time one session's lease lapses.) Fix (c) with the same change: on a generation mismatch with no entry, return the read's own answer uncached rather than `None`.
- **Test (fails on this head):** in `rvt.rs`, publish a tombstone on a replica holding the active row, advance past `OBSERVED_ROUTE_LEASE`, start a lookup behind `route_store_gate` and abort the task, clear the gate, look up again: the answer must not be active and `view_reads` must stay 0. Second case: Authority returns `Err` for the replacing read.

### B2. An `Observed` entry is retired when its floor is met even though the view cannot answer; in the legacy layout E1c raises the routing quorum rate instead of leaving it alone
- **Contract:** §5 "Legacy session layout — routes: authority"; record §3: "the cache then behaves as before E1c (`Observed` for one lease)". §4.4: degraded mode is "exactly today's behaviour: one quorum read per session per second".
- **Evidence:** retirement is decided by `floor_met(fact)` alone (`ms.rs:3495, 3507-3513`), and `AppliedView::floor_met` knows nothing of the layout (`av.rs:814-826`). In the legacy layout with a healthy proof: quorum read → `Observed{t}` → the next confirmation started after `t` applies here (mean about half of `QUORUM_WATERMARK_REFRESH`, 500 ms) → the next lookup retires the entry → `applied.route()` → `LegacyLayout` → Authority (`av.rs:1081-1083`, `:1101-1108`) → a new `Observed`. The entry lives one sampling period, not one lease.
- **Failure:** on a cluster that has not run the coordinated Source installation — the record says the fleet may be one ("says whether the fleet's gain waits on that installation") — each watched session costs two to three `routing` quorum reads a second where `ROUTE_CACHE_TTL` cost one. The lane ships as a regression of the number it exists to lower, and nothing reports it: the per-lease bound is tested only with the proof *absent* (`rvt.rs:448`). The same loop runs for any standing fallback that is not a missing proof: `unregistered`, or `local_error` while this replica trails the layout rebuild.
- **Fix:** retire only into a view that can answer. Give `RouteView` one predicate (layout installed and slot registered) and have `cached_route` keep an `Observed` entry for its full lease while it is false; or have `floor_met` for the route table answer `false` in the legacy layout. Before deploy, read the fleet's layout and put it in the record.
- **Test:** daemon case over a double that answers Authority with the proof held and every floor met: quorum reads over 2.2 s are ≤ 3, as in `without_a_proof_quorum_reads_are_one_per_session_per_lease`.

## Should-fix

1. **`Absent` from the view is final for media routing; a peer's activation not yet applied here is answered from the local path.** `relay_if_remote` confirms `OwnerTransition | Terminal` by quorum but returns `Ok(None)` for `Absent` (`http/hls/relay.rs:26-27`). Before E1c a first lookup was a quorum read, so `Absent` was true at read time; now it is the replica's answer, up to the proof's bound behind. A third node N receiving the first playlist GET for a session P activated a moment ago finds no row, falls to the local path, whose verdict read then says `ActiveRemote` and returns `response_owner_transition` 503 (`http/hls/response.rs:353-368`) or `VodResurrection::Unavailable` (`http/hls/segment.rs:506-521`) instead of relaying. §4.4 says the view "never ends" a request; `status.rs` honours that for `Absent`, the relay does not. *Fix:* where the local path already takes its verdict read and gets `ActiveRemote`, relay once to that owner; that costs random ids nothing new (they already pay that verdict read). Or rule that the 503-and-retry is accepted and say so in §5.
2. **The fence guard would not catch a fence moved through a private helper — the way E1b's first build failed.** (a) `the_fence_bodies_never_name_the_applied_view` (`rvt.rs:601-632`) checks four functions for three names; `route_resolution_at`, `media_route_resolution_at`, `cached_route` and `self.routes` are not banned, and takeover, release and the renewal path in `ms.rs` are not in the list. (b) `a_fence_never_reads_the_view` (`rvt.rs:566-598`) runs with an empty cache, where `cached_route` makes no trait call (`ms.rs:3483-3485`): a fence that consults the cache first passes with `calls == 0`. It also never reaches `authorize_prepared_media_before`'s store branch (the route is `ActiveLocal`), `verify_authority`, the receipt fences, takeover or release, all named in §8. (c) `inv.rs:291` counts `.route(` only on a receiver spelled `applied`; `AppliedView::route(x, ..)` — the form `ms.rs:1051` itself uses — `RouteView::route(..)`, and an `Arc<dyn RouteView>` under another name are invisible, and E1b's handle-name pin matches the text `AppliedView`, not `dyn RouteView`. *Fix:* pin every caller of `raw_route_before`, `route_resolution_at`, `media_route_resolution_at` and `cached_route` by enclosing function; prime a current `View` entry before the runtime guard and assert the fence still returns Authority's row when the two differ; count `RouteView` handles and path-qualified `route(` calls.
3. **Eviction takes the lowest sequence even when it is an unretired `Observed`, and that closes the route view for every session.** `ms.rs:3594-3619`. Entries no longer expire, so the cache sits at `MAX_ROUTE_CACHE_ENTRIES` in steady state and every new key evicts. Once ~4,096 distinct ids are inserted inside one table revision (an unauthenticated spray, which this cache is documented to bound, `ms.rs:2709-2713`), the victim is the oldest entry, which can be a publication of the last half second: `hold_floor` → every `View` entry answers `Closed(Floor)` and is removed (`ms.rs:3492, 3513`) → every watched session takes a quorum read, each a fresh `Observed`, each evictable in turn. A view read admitted just before `hold_floor` also returns its pre-fact row once. *Fix:* victim order — a stale `View`, then the oldest `View` or retirable `Observed`, an unretired `Observed` only when nothing else exists. `a_cache_miss_storm_under_one_proof_costs_no_quorum_read` uses exactly 4,096 ids and no publication, so it never evicts; extend it past capacity with one published fact present.
4. **The deferred route cases are partly needed before merge.** The multi-node learner-join, restart and leader-change cases can follow in `cluster-integration-tests`. What cannot wait is the cache's own behaviour across those events, which no test touches: the double has no generation and no mid-flight proof loss. Add, on the double: image replacing (odd generation) with a `View` and an unretired `Observed` entry present — `View` goes to Authority, `Observed` is neither retired nor replaced by a view answer, and both recover after; proof lost between the exclusive check and the read; and the B1/B2 cases above. Also `status.rs` has only a string-shape test (`inv.rs:324-351`): add a runtime case that a non-active view verdict is confirmed by one quorum read and that a stale `ActiveRemote` is reclassified.
5. **SQLite: every lookup is now a store read under the single-flight shard.** No stamp, so nothing is cached (`ms.rs:3059`), and an `Observed` entry is retired at once (`av.rs:816`). §4.2 "Standalone" allows the read; what it does not weigh is that the hot path of a standalone server — every segment and playlist GET — went from a map hit to a `route_queries[shard]` lock held across a blocking-pool read (32 shards). Measure `plurx_media_session_route_lock_seconds` and segment latency on a standalone node under several concurrent players before merge, or keep `Observed` entries for their lease on SQLite as the old cache did.

## Nits

1. `control_route`'s comment still says "one-second TTL" (`ms.rs:3088-3089`); `FactInstant`'s doc says `note_fact` is its only constructor (`av.rs`, above `struct FactInstant`) — `observe` is another.
2. Entries never expire, so the cache holds up to 4,096 rows with `recipe_json` and `response_json` of long-ended sessions, and `plurx_media_session_route_cache_entries` reads the cap, not the live set. Say so in the metric help and `docs/OPERATIONS.md`, or drop the two JSON bodies from negative and terminal entries.
3. `last_fallback` is one cell for both views (`av.rs:322`): a settings `floor` fallback hides `legacy_layout`. The Developer row should state outright when the route view is waiting on the principal layout.
4. `rvt.rs:333` and `:448` run on the wall clock with 40-50 ms sleeps and assert `checks > 10` and `requests >= 30`; on a loaded CI runner those are the first to flake.
5. An `authoritative_*` verdict that contradicts a cached `View` entry leaves the entry in place (`ms.rs:2838-2873`), so each request repeats relay → refusal → reclassify until the slot moves. Dropping the `View` entry there is one line.
6. `validation_assume_installed_session_layout` is `pub` under a feature `crates/plurx-cluster-check/Cargo.toml:18` enables on `plurx-core`; a workspace-wide build unifies it into `plurxd`. No production caller exists; a source pin that none appears would keep it so.
7. `plurx_media_session_route_reads_total{source="view"}` and `lookups_total{result="view"}` count SQLite store reads as view reads; the help text should say so.
8. Pre-existing, but B1(c) leans on it: a generation-shard mismatch returns `None` for a session with no cache entry even though the read found its row (`ms.rs:3557-3564`).
