# Playback start — E1 build contract: adversarial review

**Status:** complete — review of [PLAYBACK-START-E1-BUILD.md](../streaming/PLAYBACK-START-E1-BUILD.md) against `main @ 0c57d812`, from source only (nothing compiled or run).
**Reviewer:** Claude (claude-fable-5-2, session 01BCWL9xwmpSjitHqZMTRAht), 2026-11-11.
**Verdict:** do not build as written. 6 blockers, 9 should-fix, 6 nits. The proof mechanism itself is sound; the blockers are in read-your-write, the snapshot flag pairing, and the call-site table.

Paths are relative to the repo root; `ms.rs` = `crates/plurxd/src/media_sessions.rs`, `mig.rs` = `crates/plurx-core/src/cluster/migration.rs`, `writer.rs` / `sm.rs` = `vendor/hiqlite/src/store/state_machine/sqlite/{writer,state_machine}.rs`, `http/` = `crates/plurxd/src/http/`.

## What holds (checked, no finding)

- **Applied ⇒ visible.** `apply` awaits the writer's reply for every entry (`sm.rs:1166-1175, 1307-1326`), so openraft's `last_applied` never precedes the SQLite commit. A proof (`mig.rs:6169-6240`) therefore means the read pool sees at least a quorum-confirmed index whose confirmation started < 1 s ago on this node's monotonic clock (`mig.rs:6226-6229, 6338-6342`); no cross-node clock is compared.
- **Restart, leader/term change, deposed leader, lag:** covered by `bound_to_current_generation` (`mig.rs:5791-5808`) and the per-confirmation lease. The image never moves backwards on a leader change (only committed entries are applied).
- **Snapshot restore is atomic to readers in the common case** (backup into the writer connection, `writer.rs:690`), and a node that needs a snapshot has no proof anyway; the generation parity is a second guard, not the only one.
- **Route site list is complete:** `rg '\.media_session_route\(|route_resolution_before\(|\.control_route\('` over `crates/plurxd/src` finds no site missing from §6.1.
- **Repo rules:** no gate, no switch (matches `AGENTS.md:128-134`); no new spawn or timer; no new `query_consistent*` site. `plurx_playback_rolling_terminal_events_total{event="authority_fence"}` exists (`playback_control.rs:15818`).

## Blockers

### B1. The authored overlay is dropped after one resolution; a lagging replica then revives the pre-write row
- **Claim (§4.4):** on a slot move with a mismatching view row, take one quorum read and cache it as `Origin::View` under the pre-read stamp; "the replica's catching up bumps the slot".
- **Evidence:** the slot is per table and bumps on *any* `media_sessions` apply, not on reaching this write's index. Follower F commits a release at index W while its replica is at W−3, and W−2 and W−1 are other owners' renewals (lease 12 s, `ms.rs:126`, so the table is written about once a second cluster-wide). W−2 applies → mismatch → quorum read → terminal cached as `View`. W−1 applies → that entry is invalid → local read at W−1 returns the **active** row → served, because the proof is anchored on a confirmation ≤ W−1 that is still inside its lease (`mig.rs:6219-6239`; `serving_proof_remains_valid` deliberately ignores lag, `mig.rs:6307-6317`). The tombstone exists precisely so a released session cannot "fall through to a still-live local actor" (`ms.rs:2991-2994`). The same sequence reverts a takeover to the old owner and an activation to "absent". Any fallback quorum result has the same non-monotonic re-read.
- **Fix:** an authored (or quorum-read) entry stays authoritative until a local read **matches it or is newer by `(owner_epoch, state)`**; a mismatch re-arms the entry instead of replacing it with `View`. Or carry the commit index: extend `WriteAck` to the session transaction path (declared out of scope in §10 — it is the direct fix) and hold the entry until `applied_index ≥ W`. Add the test: two unrelated `media_sessions` applies before the node's own release applies; the route never returns active.

### B2. The even flip is paired at one of three `SnapshotApply` senders; a node that boots through a restore keeps the view closed for the life of the process
- **Claim (§4.1, §5):** odd before `conn.restore`, even "only after `reconnect_read_pool` returns (`state_machine.rs:1499-1507`)"; start-up recovery is left as "builder verifies".
- **Evidence:** `SnapshotApply` is also sent by `update_state_machine_` (`sm.rs:763-780`), called at start-up when the database file is absent and a snapshot exists (`sm.rs:402-407`) and by `recover_pending_snapshot` (`sm.rs:838`). Neither is at `:1499-1507`. Under the contract the writer makes the mark odd and nothing makes it even: every read is a quorum read, silently, which is the "after restart" case plan §3 E1 requires the view to survive.
- **Fix (and the simpler mechanism already present):** `snapshot_recovery_pending` (`sm.rs:305`) is already set before every restore and cleared after the pool reconnect (`sm.rs:832/843, 1473/1512`). Put the "image replacing" signal and one `generation += 1` at the two points that reconnect the pool (`update_state_machine_` and the install task), not in the writer arm. No parity, no cross-thread pairing. Test: start a node with no DB file and a current snapshot; the view opens.

### B3. The settings save response is moved to the view
- **Claim (§4.3):** "the handler writes, then answers from its own quorum snapshot (`http/system.rs:3787, 4812`)"; §6.3 moves `:2732` ("`GET /api/v1/settings`").
- **Evidence:** `:3787` and `:4812` are pre-mutation reads. The PUT response is `settings_dto(&state)` at `http/system.rs:4872`, and `settings_dto` reads at `:2732` (`:2726-2732`); GET is the other caller (`:3263`). Moved as written, a save through a follower answers from a replica that has not applied it. The web client renders that response (`cacheSettings(await api("/settings",{method:"PUT"…}))`, `crates/plurxd/src/web/pages/settings-developer.js:86-301`), so the switch snaps back; the DTO also carries `live_tv_config_generation`, which the next save must echo or get 409 (`http/system.rs:3662-3670`).
- **Fix:** `settings_dto` takes its source; `:4872` stays authority. See B4 for GET.

### B4. Settings have no read-your-write, and one moved site depends on it by design
- **Claim (§6.3):** `http/hls/preparation.rs:1921, 2442` and `http/shared_receiver_control.rs:329` move ("per-request preference reads").
- **Evidence:** saving `prepared_quality_handoff` off takes the transition write lock, writes, and settles successors (`http/system.rs:4469-4487`); `preparation.rs:2434-2444` holds the read side "through the final setting read and stage" so "no detached candidate may reserve after this write". On a follower the view can still answer "on" after the lock is released (put acked by the leader, not yet applied here, proof valid): the race the lock closes is reopened on the saving node itself. `http/hls/control.rs:2547` is self-described as "after routing, before any owner mutation".
- **Fix:** (a) those four sites stay authority, by the contract's own rule; (b) give the view real read-your-write: settings writes are `execute` (`store/hiqlite.rs:6198-6201`), which `WriteAck` covers (`vendor/hiqlite/src/client/execute.rs:20-23`). Record the highest acked settings index per process and require `mark.applied_index ≥` it; `log_index: None` ⇒ authority until the next reload. That is the only caller `min_applied_index` has — today the contract defines it and nothing supplies it.

### B5. Status is reclassified against the contract's own rule
- **Claim (§6.1, §12-5):** `http/hls/status.rs:39, 64, 141` become view-first, "quorum only to confirm a non-active verdict".
- **Evidence:** `:141` is the reclassification after a relayed peer answer — the `relay.rs:113-122` pattern that §4.4 says stays ("Final verdicts stay quorum reads"). `:64` is the post-publication half of a pre/post bracket around reading local actor state (`status.rs:36-38, 55-75`, `same_route_authority`); a stale view `ActiveLocal` is a positive answer, so no quorum read would follow and a released session's lingering actor publishes status. Astra's row: "Preserve pre/post pending-release checks and authoritative … fence paths".
- **Fix:** only `:39` may go view-first (it is routing); `:64` and `:141` stay. Re-ask §12-5 with that framing and report the floor (§9-5).

### B6. "Advisory" route reads are fences before a claim
- **Claim (§6.1):** `link_receipts.rs:492, 610, 627, 947, 1014`, `prepared_link.rs:357, 426`, `candidate_recovery.rs:86` → view; "a stale row only drops a measurement".
- **Evidence:** a stale row can also *admit*. `http/hls/link_receipts.rs:1022-1037`: "Claim only after its current authority fence", then `row.claim(...)`. `prepared_link.rs:426-457` checks `active`/owner/epoch/`PUBLICATION_BLOCKED` and then `register_staged`. `candidate_recovery.rs:79-86` precedes "the durable observation".
- **Fix:** `:1014`, `prepared_link.rs:426` and `candidate_recovery.rs:86` stay; the others move only after each is shown to have no write behind it. `http/system.rs:1176` is fine.

## Should-fix

1. **No bound on quorum reads without a proof.** Rule 4 needs a proof at hit time, and §4.4 deletes the TTL, so with no proof (lag, leader gap, a rolling upgrade's protocol mismatch `mig.rs:5807`, which lasts minutes) every routed media request is a quorum read; today it is one per session per second (`ms.rs:143, 3795`). The serving fence does not reject requests, and sessions run through a 5 s grace (`serving_fence.rs:415`). Fix: a quorum-read result is itself a quorum confirmation — let it stand for one `QUORUM_WATERMARK_LEASE` from the read's start when there is no proof. That is the proof's own bound, not a second TTL; say so in §2. Add the degraded-mode read rate to §9-4.
2. **SQLite contradiction.** `eligible_serving_proof()` is `None` on SQLite (`mig.rs:6166-6168`), so rule 4 never hits and §4.5's "`Origin` works unchanged" is false. State that the proof test is vacuous for the standalone backend, and test it.
3. **Publish before the reply, and not "at the end of each arm".** Every arm replies inside itself (`writer.rs:346, 591-595, 632-640`) and several `continue` early (`:312-316, 339-342, 436-441, 782-786`). Publishing after `tx.send` lets a memo hit serve the old value after the write is acked on this node. Publish immediately after the commit and before `send`, from one helper that also runs on the `continue` paths (or at the top of the next loop iteration).
4. **DDL and table rebuilds do not fire the update hook.** `Batch` (`writer.rs:606-641`, non-transactional) and `Migrate` (`:644-655`) carry DDL; a rebuild (`CREATE new … DROP … RENAME`) reports the temporary name only. Bump every slot (or the generation) at the end of those two arms. Also add to §4.1's limits: no hook for rows removed by `ON CONFLICT REPLACE`.
5. **64 hashed slots over ~240 tables.** The chance `media_sessions` shares its slot with no other table is about 2 %; a busy neighbour invalidates at its write rate — the cost §12-2 says the hook avoids. Register the viewed tables for dedicated slots and ignore the rest (cheaper per row than hashing every table name on bulk catalogue writes). `media_playback_pointers` is not in the route projection (`store/hiqlite_sessions.rs:2028-2045`); drop it from the viewed set.
6. **The local route twin ignores the session layout.** Route SQL is a template resolved per layout, and while the layout is `Legacy` every read is followed by a consistent re-check (`hiqlite_sessions.rs:386-420, 636-665`). The twin may run only when `media_session_projection == 2`; otherwise authority. One line in §4.4, one test.
7. **Expected hit ratio is not stated and the headline test hides it.** With per-table invalidation and about one `media_sessions` write a second, cached routes live about as long as today; the gain is local read vs quorum read, one `spawn_blocking` pool read per request (`vendor/hiqlite/src/query/mod.rs:46-48`) behind the per-shard mutex (`ms.rs:2581`). "An hour with no applied change" is an idle cluster. The hook already receives the rowid — either justify per-table with E1a numbers (`reloads_total{view="routes"}` against request rate, read-pool wait) or scope per-row in.
8. **"Each fails against `0c57d812`" is not true of every test.** Guards that pass today: pending-release ordering (`ms.rs:2613`), lease expiry by clock, "a fence never reads the view" (vacuous before the view exists). Label them guards and give each a counterfactual mutation. The stale-replica tests cannot use `validation_wait_for_apply`: it is one process-global flag (`sm.rs:37-41, 161-176`) and would pause the leader too in an in-process three-voter fixture — use the instance-local precommit hold (`writer.rs:54-65`) or add a per-instance apply hold. These tests need `--features cluster-read-cost-validation`, not only `hiqlite-contract-tests` (`crates/plurx-core/Cargo.toml:21, 30`; `store_contract.rs:29947`).
9. **Acceptance item 2 is not readable from `/metrics`.** `local_active_sessions` is a field of the cluster-operations JSON (`http/cluster_operations.rs:137, 1339`), not a series. Name the series or add one in E1a. Role labels are six, not three (`http/mod.rs:133-136`).

## Nits

1. `serving_proof_remains_valid` is documented as not for reads ("the bounded-replica read path — which does need freshness — is untouched", `mig.rs:6307-6312`). Using it is defensible (time-bounded), but §4.2's "tighter than the catalogue reader's 64-entry budget" is wrong: the time bound is the same and the entry lag is unbounded. Either use `run_bounded_replica_after(0, …)` (`mig.rs:6112-6133`) or reword and amend that comment in the same PR.
2. The consistent read discards `ensure_linearizable`'s read index (`vendor/hiqlite/src/query/mod.rs:29`). Pre-existing, but the overlay's "one quorum read resolves it" leans on it; note it.
3. Web path is `crates/plurxd/src/web/pages/`, not `web/pages/`.
4. Eviction "any stale entry, else the oldest insert" is an O(n) scan under the map lock once stale entries are no longer swept; say so, or keep the sweep keyed on stamp and keep its histogram.
5. E1a ships a Developer row and a "last minute" ratio with no caller moved; compute the window at read time (no timer) and say the row reads "no readers yet" until E1b/E1c.
6. §12-2's alternative (applied-index-only mark) should also be costed against should-fix 7: at one `media_sessions` write a second it may be nearly as good for routes and needs no `hooks` feature; settings would then want a cheap content check on reload.

## Sub-lane split

Sound in outline; reorder the content. E1a must carry B2 (flag pairing), should-fix 3–5 and the acked-index plumbing for B4, since both later lanes depend on them. E1b is blocked on B3/B4. E1c is blocked on B1, B5, B6 and should-fix 1, 6; with B5/B6 applied its measured gain shrinks, so take E1a's per-site baseline before sizing it. E1b-2 stays out.
