# M5.5 — a successor that exists without being current

**Status:** the store half is built · **Executes:** §2.2 of
[REMAINING-ROADMAP-HANDOFF.md](REMAINING-ROADMAP-HANDOFF.md), the durable half
of M5.5 · **Written:** 2026-08-31 · **Baseline:** `main` at `db6b7625` ·
**Sibling:** [M5.5-PREPARATION-FEASIBILITY-SPIKE.md](M5.5-PREPARATION-FEASIBILITY-SPIKE.md),
the measurement half, which needs hardware and gates M6 rather than this

Companion to [REMAINING-ROADMAP-HANDOFF.md](REMAINING-ROADMAP-HANDOFF.md)
(what the remaining milestones are) — this is *the store work M6's transaction
sits on*, written so nobody has to rediscover the schema or the three traps in
it.

The two halves of M5.5 are independent. The spike measures what clients can
promise; this builds the durable state a promise gets recorded in. Neither
blocks the other.

## 1. The finding that decides the whole shape

> **`activate_media_session` is the only way to create a durable successor
> session, and it unconditionally reaps the predecessor and advances the
> pointer to itself.**

Calling it to "stage" a successor retires the stream the viewer is watching
and repoints them at a session that has not produced a byte. Adding a flag to
it is worse than it sounds, for a reason in §3.3.

**Prepare needs its own Store entry point.** That is the milestone.

Everything else here exists to stop a staged row being noticed by machinery
that has every right to assume a row like it is current.

## 2. The ground, verified at `db6b7625`

### 2.1 `media_playback_pointers`

SQLite migration **v25**, `crates/plurx-core/src/store/sqlite/mod.rs:705`;
Hiqlite `MEDIA_PLAYBACK_POINTERS_SCHEMA`,
`crates/plurx-core/src/store/hiqlite_sessions.rs:87`. Identical shape:

```sql
CREATE TABLE media_playback_pointers (
    user_id                INTEGER NOT NULL,
    playback_id            TEXT NOT NULL CHECK (length(playback_id) BETWEEN 1 AND 128),
    current_incarnation_id TEXT NOT NULL UNIQUE,
    updated_at_ms          INTEGER NOT NULL,
    PRIMARY KEY (user_id, playback_id)
) STRICT;
```

Two constraints matter: one pointer per player, ever; and
`current_incarnation_id` is **globally** unique, so an incarnation can be
pointed at by at most one pointer row.

**Current schema versions: SQLite 38, Hiqlite 19.** Yours are 39 and 20.

### 2.2 "Which session is current" is pointer-keyed and nothing else

`MediaSessionStore::media_session_route_for_playback`
(`store/mod.rs:2254`) resolves *only* through the pointer:

```sql
SELECT {ROUTE_COLS} FROM media_sessions
  WHERE incarnation_id = (SELECT current_incarnation_id
    FROM media_playback_pointers
    WHERE user_id = ?1 AND playback_id = ?2)
```

`media_sessions` has **no `created_at` column**, and there is no `ORDER BY`
anywhere in either backend that picks a session by recency for a playback. So
an extra row for the same playback changes this lookup's answer by exactly
nothing.

**This is good news and it is the reason the milestone is tractable**: a
staged row that holds no pointer is already invisible to the one query that
decides what is current. The work is in the other four places it is *not*
invisible.

### 2.3 The supersession reap

It is not a function. It is three `tx.execute` calls inside
`activate_media_session`, run on every non-replay activation. The retirement
itself, `store/sqlite/sessions.rs:604`:

```sql
UPDATE media_sessions SET state = 'ended', terminal_reason = 'superseded',
       lease_expires_at_ms = ?1, publication_ready_at_ms = ?5, updated_at_ms = ?1
  WHERE incarnation_id = (SELECT current_incarnation_id
    FROM media_playback_pointers WHERE user_id = ?2 AND playback_id = ?3)
    AND incarnation_id != ?4 AND state != 'ended'
```

**The predicate is exactly: the incarnation the pointer names, that is not me,
that is not already ended.** No time window, no consent. Its two companions in
the same transaction drop the victim's `cache_consumer_pins` (`:618`) and
collapse its job lease (`:632`).

A staged row holds no pointer, so it is not the victim. It is also not the
beneficiary, because it is not the one activating. Prepare must simply not run
these three statements.

### 2.4 SQLite and Hiqlite do not agree here, and you must not inherit that

The replicated twin (`hiqlite_sessions.rs:862`) carries two guards the SQLite
version does not:

```sql
    AND EXISTS (SELECT 1 FROM media_sessions
      WHERE incarnation_id = $5 AND session_id = $6
        AND owner_node_id = $7 AND state = 'active')
    AND $8 != '' AND incarnation_id = $8
```

`$8` is `predecessor_incarnation`. **The replicated backend already refuses to
reap anything but the named expected predecessor; the SQLite backend will reap
whatever the pointer happens to name.** Today that difference is invisible
because both are reached the same way. Build prepare on top of
`activate_media_session` and the two backends will diverge under exactly the
conditions M6 exists to create.

## 3. The four places a staged row is visible, and what to do about each

### 3.1 The user admission cap — it counts, and that is a real limit

`MAX_CURRENT_PER_USER = 64` (`sqlite/sessions.rs:17`). Every counting query
(`:279`, `:338`, `:517`, `:536`) excludes *exactly one* incarnation:

```sql
AND incarnation_id != COALESCE((
  SELECT current_incarnation_id FROM media_playback_pointers
   WHERE user_id = ?1 AND playback_id = ?3), '')
```

A staged successor is neither the activating incarnation nor the pointed-at
one, so **it counts against the cap for the whole preparation window**.

That is not automatically wrong — a prepared successor really does hold
resources — but it must be a decision rather than an accident, and
`media_session_same_playback_replacement_is_admitted_at_user_cap`
(`tests/store_contract.rs:2941`) pins today's behaviour at exactly 64. Either
exclude staged rows from the count and say why, or keep them counted and
document that preparing halves a heavy user's headroom.

### 3.2 Maintenance will retire a staged row as `replaced`

`maintain_media_sessions` (`sqlite/sessions.rs:2148`):

```sql
UPDATE media_sessions SET state = 'ended', terminal_reason = 'replaced', …
  WHERE incarnation_id IN (SELECT incarnation_id FROM media_sessions
     WHERE state = 'active' AND lease_expires_at_ms <= ?3 …)
```

A staged row is `state = 'active'`, so 60 s past its `lease_expires_at_ms`
maintenance ends it. **Decide deliberately which clock owns expiry**: either
the preparation lease is authoritative and maintenance is its backstop (arm
`lease_expires_at_ms` to the preparation deadline and let this fire), or the
staged row renews and expiry is the actor's alone. Do not leave two clocks
racing.

The pointer reaper beside it (`:2188`) deletes pointers whose session is gone
or not active. A staged row holds no pointer, so it is a no-op — nothing to do.

### 3.3 Takeover inventory — free, if you keep the sentinel

`expired_media_sessions` (`:1721`) and `owned_media_sessions` (`:2276`) both
already exclude rows whose `publication_ready_at_ms != MEDIA_SESSION_PUBLICATION_BLOCKED`
(`i64::MAX`, `domain.rs:949`). **A staged row that stays at that sentinel is
invisible to takeover for free.**

This is also the answer to "why not a flag on `activate_media_session`": the
sentinel already means *not publishable*, and activation writes it and then
arms it. A staged row wants the first half and not the second, which is a
different lifecycle, not a different argument.

### 3.4 `terminal_reason` is a CHECK-constrained enum

`('deleted', 'superseded', 'admin_stop', 'revoked', 'replaced')` —
`sqlite/mod.rs:2851` (migration v34) and `hiqlite_sessions.rs:171`. An aborted
or expired staged successor arguably wants its own cause.

**Widening it on SQLite means a table rebuild**, the way v37 did for
`fragment_indexes`. If `replaced` is honest enough for an aborted successor,
reuse it and save the migration; if it is not, budget the rebuild rather than
discovering it late.

## 4. The CAS idiom — copy it, do not invent one

Two established shapes. Use the first for prepare, abort and expiry; commit
must be the second.

### 4.1 Guarded UPDATE, then read back and filter

`arm_media_session_handoff` is the cleanest example
(`sqlite/sessions.rs:1149`, replicated twin `hiqlite_sessions.rs:1427`):

```rust
tx.execute(
    "UPDATE media_sessions SET publication_ready_at_ms = ?1, updated_at_ms = ?2
      WHERE incarnation_id = ?3 AND owner_node_id = ?4 AND owner_epoch = ?5
        AND state = 'active' AND publication_ready_at_ms = ?6",
    params![…],
)?;
let route = tx.query_row(…)
    .optional()?
    .filter(|route| route.owner_node_id == owner_node_id && …);
```

Three properties to preserve:

- the return type is `Result<Option<MediaSessionRoute>, StoreError>`, and
  **`Ok(None)` means the CAS lost**. `Err` is for malformed input and real
  database faults. Callers never see a bool.
- the outcome is derived from a **re-read plus a predicate**, never from
  `rows_affected` — deliberately, so an idempotent replay that finds the row
  already in the target state returns `Some` rather than a spurious loss.
- Hiqlite does the re-read **outside** the write, because
  `hiqlite::Client::txn()` takes a fixed statement list and cannot read,
  branch or `RETURNING`. Every precondition is inlined into each statement's
  `WHERE` / `WHERE EXISTS`.

`replicated.rs:52` already offers `CasOutcome` / `classify_cas` if you want
`rows_affected` semantics, and treats 2+ affected rows as an error rather than
a success. It is currently used only by its own test; it is the sanctioned
name if you need one.

### 4.2 Commit: the all-zero-transaction replay discriminator

Commit must move the pointer and mark the action committed atomically, which
is the shape `activate_media_session` already has (`hiqlite_sessions.rs:998`).
The problem it solves is that an all-zero replicated transaction is ambiguous
between *I lost every precondition* and *I am an exact replay*, so it
disambiguates with an exact post-commit projection: re-read the route, re-read
the pointer, require both to match.

**The committed-pointer CAS the plan asks for already exists** —
`hiqlite_sessions.rs:921` — as the pointer advance with
`predecessor_incarnation` in `$7`. Commit is that statement with `$3` set to
the staged successor. Reuse it rather than writing a second one.

Note `hiqlite_sessions.rs`'s own `mod tests` (`:2758`) asserts on the **source
text** of `activate_media_session` — four literal substrings and a
`matches(...).count() == 2`. If your commit path lives in that method those
assertions need updating; if it lives in a new method, write the equivalent
guards for it, because they are what stops the discriminator being quietly
deleted.

### 6.1 The deadline idiom to copy

`PendingProducerAction` (`:2662`) is the model for a preparation lease: a
kind enum whose `deadline_reason()` maps to a typed `ProducerDecisionReason`,
a struct carrying `action_sequence` / `producer_attempt` / `deadline`, armed
in one place with a budget const, folded into `next_deadline()` with one more
`.min(...)`, and settled by a `settle_…_deadline_at(now)` that returns `bool`.

Two rules from it, both load-bearing:

- **Session lifecycle is always the higher-priority clock.** `claim_expiry_at`
  (`:7098`) is checked first; a preparation lease aborts the *successor*,
  never the generation.
- A preempted deadline whose `producer_attempt` no longer matches is
  observation-only: clear it and return `false` rather than committing a
  decision for an attempt that is gone.

### 6.2 The ownership ledger — half in scope

`tests/playback/rolling-producer-owners.toml` has two scopes.
`[[symbols]]` counts against `transcode.rs` only, so `playback_control.rs` is
**out**. `[[module_symbols]]` and `[[module_structures]]` count against every
`*.rs` under `crates/plurxd/src`, so it is **in**.

Practically: a genuinely new name matches no watched pattern and needs no row
— the ledger is an allowlist of watched patterns, not a census. But the
structural rows *will* move if you add any timer or task shape.
**Arm the new deadline through `next_deadline()` rather than a new sleep or
spawn and the counts do not move at all.**

## 7. Acceptance

From roadmap §2.2, made checkable:

1. **Prepare leaves the predecessor current and running.** After a prepare,
   `media_session_route_for_playback` returns the predecessor unchanged, the
   predecessor's `state` is still `active`, and its `terminal_reason` is still
   `NULL`.
2. **A staged row is invisible to ordinary current-session lookup.** Same
   query, same answer, with and without the staged row present.
3. **Prepare neither calls the supersession reap nor advances the pointer.**
   Assert the predecessor was not marked `superseded`, and that
   `media_playback_pointers.updated_at_ms` is unchanged — that second one is
   the assertion that catches a prepare built on `activate_media_session`.
4. **One staged successor per playback.** A second prepare against a playback
   that already has one is refused, not silently accepted.
5. **Commit advances the exact expected pointer once.** A commit whose
   expected predecessor is stale returns `Ok(None)` and **aborts the staged
   generation rather than reaping a newer player generation** — that clause of
   the plan is the one worth a dedicated test.
6. **Abort and expiry remove only the staged successor.** The current stream
   stays authoritative and playable.
7. **Owner death during every phase leaves one durable outcome.**

Run them with `cargo test -p plurx-core --test store_contract media_session`
(SQLite memory + file, no features — this is the fast loop and it is what
`make unit` runs). `--features hiqlite-contract-tests` boots three real voters
and runs every scenario a third time; that is `make cluster-check` territory
and belongs at the gate, not in the loop.

## 8. What was decided, and where it landed

The store half is built. Four decisions §3 left open were taken here rather
than deferred, each one because leaving it open is what makes a staged row
dangerous.

**§3.1, the admission cap: staged rows count.** A prepared successor holds a
real encoder slot, and a preparation that did not count would let a heavy user
hold twice the sessions the cap names by keeping one staged forever. The price
is that preparing halves a saturated user's headroom, which is the honest cost
of the resource. `media_session_same_playback_replacement_is_admitted_at_user_cap`
still pins 64 and still passes.

**§3.2, the expiry clock: one, not two.** The staged row's
`lease_expires_at_ms` *is* the preparation deadline, so the retirement sweep in
`maintain_media_sessions` — which ends any overdue `active` session — is the
backstop rather than a competitor. A new ledger reaper beside the pointer
reaper then releases the one-per-playback slot. It is keyed on the successor's
*state*, never on the deadline, so it can never race a live preparation.
`media_session_maintenance_reaps_an_abandoned_preparation` is acceptance 7.

**§3.3, the sentinel: kept.** A staged row is born at
`MEDIA_SESSION_PUBLICATION_BLOCKED` and never arms it, so it is invisible to
`expired_media_sessions` and `owned_media_sessions` for free.
`preparation_route_matches` asserts it on every replay, so a row that armed is
not accepted as staged.

**§3.4, `terminal_reason`: `replaced`, no migration.** An abandoned successor
really was replaced — by the predecessor it never displaced — and widening the
CHECK on SQLite is a table rebuild.

### The admission cap, revised

The first version copied activation's counting query verbatim, including its
exclusion of the pointed-at incarnation. That exclusion is correct *there*
because the same transaction is about to reap that session. A preparation reaps
nothing, so discounting the predecessor counted a slot that was not being
freed and admitted one session past the cap — 65 live sessions at
`MAX_CURRENT_PER_USER = 64`. Prepare's count therefore excludes only the
staged row itself, which is the fifth spelling of that query and deliberately
not the same as the other four.

### The staged row takes its own lease

`renew_media_sessions`'s first statement is an `UPDATE` on
`session:<incarnation>` in `job_leases`, and `claim_media_session_takeover`
requires the same row to exist. A staged row inserted without one — the first
version — could never be renewed or taken over, so a *committed* successor
kept the preparation deadline as its lease and was ended by maintenance at the
moment the preparation would have expired, taking the playback's pointer with
it. Prepare now takes the lease exactly as activation does, and commit moves
both the row and the lease off the candidate clock onto the caller's serving
boundary. That is why `commit_media_session_preparation` takes a
`lease_expires_at_ms`.

### Divergences the tests caught, and one they did not

The first SQLite abort branched on `rows_affected` and returned `Ok(None)` on a
replay, while the replicated twin re-read and returned `Some`. That is the
§2.4 failure mode in miniature, found by running the same scenario against both
backends. Both now derive the outcome from a re-read plus a predicate.

The fix for it introduced a worse one, which review caught and the tests had
not: making the outcome a predicate over the *return value* left the writes
ungated. `abort_media_session_preparation` takes an incarnation id, and an
incarnation id names any session in the database — so an abort for a playback
it did not belong to ended a stranger's live stream, deleted its cache pins,
clamped its lease, and then reported that it had lost. The maintenance pointer
reaper deleted that playback's pointer on the next pass. A late abort of a
successor that had already committed did the same to the stream it had just
promoted. Every write is now gated in the SQL: the retirement on the ledger
row, and the pin delete and lease clamp on that retirement having fired at this
instant — the replicated twin's shape, which was right all along.

Two more the replicated backend had and SQLite did not, or the reverse:
Hiqlite had no ledger reaper at all, so a dead owner's preparation held the
one-per-playback slot forever on a cluster; and Hiqlite's commit returned
`Ok(None)` for a retry that arrived after a *later* preparation existed, where
SQLite correctly read the committed route back. Both are fixed, and both now
have a scenario in `store_contract.rs` rather than only a reading of the SQL.

**The lesson worth carrying to M6.** Every one of these was found by comparing
the two backends statement by statement, not by a test — the replicated path
only runs under `--features hiqlite-contract-tests`, so the fast loop exercises
exactly half of what this milestone builds. The source-text guards in
`hiqlite_sessions.rs`'s own `mod tests` (§4.2) are the substitute, and three
were added here: the commit discriminator, prepare's two prohibitions, and the
abort's gating.

## 9. Non-goals

- **Do not add a flag to `activate_media_session`.** §1 and §3.3. The two
  backends already disagree about what that method may reap (§2.4), and a
  flag inherits the disagreement.
- **Do not build the eight-phase transaction here.** This milestone builds the
  rows the transaction writes to. M6 builds the transaction, and it is gated
  on the spike, not on this.
- **Do not let a staged row acquire a pointer before commit.** Every trap in
  §3 is downstream of that one rule.
- **Do not invent a CAS reporting convention.** §4.1 exists so all of them
  read the same way to the next person.
