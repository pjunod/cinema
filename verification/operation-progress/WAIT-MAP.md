# Operation progress wait map — durable library work from claim to reply

**Status:** source-traced for model design · **Source base:** `caf93319ce833f3d8f20f3a7bcbadcbae9c1c42a` · **Written:** 2026-10-21.

This map supports [Operation progress](../../docs/cluster/OPERATION-PROGRESS-IMPLEMENTATION.md). It follows one `library_scan` or `metadata_refresh` job through the worker and names what must progress before a durable library request has a useful result. [Source anchors](source-anchors.json) record exact strings and whole-file hashes for load-bearing paths.

## Useful completion is the durable request reply

```text
readable candidate + physical admission
    -> queue claim -> scan:library:<id> domain lease -> bind both owners
    -> scan / enrich / publish catalogue rows
    -> complete request + pending waiter (fenced update)
    -> resolve a lost completion reply by reading the request
    -> release domain lease -> settle/retire queue claim -> release admission
```

A useful completion is a request and its waiter observed in a non-pending state. A catalogue insert is intermediate progress: it does not reply to the requester. A scan can return and still fail to publish the request result. Cleanup follows the request attempt and is a separate progress obligation.

## Authority and replicated-store boundaries

For `LibraryScan` and `MetadataRefresh`, `JobKind::permits_artifact_execution()` is false ([`background_jobs`](../../crates/plurx-core/src/store/background_jobs.rs#L713)). `MembershipManager::may_execute_job` therefore returns through voter-only `may_run_cluster_jobs` before learner artifact checks ([`membership`](../../crates/plurx-core/src/cluster/membership.rs#L1403)). That path reads an atomic maintenance flag and `local_node_is_committed_voter`; the latter awaits `metrics_db`, whose local-server path clones a local Raft metrics snapshot ([vendor mgmt](../../vendor/hiqlite/src/client/mgmt.rs#L541)). No app mutex was found in these authority methods.

`TimedClient::txn` applies `timeout_store` to `Client::txn` ([`hiqlite Store`](../../crates/plurx-core/src/store/hiqlite.rs#L1640), [`timeout_store`](../../crates/plurx-core/src/store/hiqlite.rs#L6700)). Vendor `Client::txn` first awaits rate limiting, then leader `raft.client_write(Transaction)` or follower stream send plus oneshot reply ([`transaction`](../../vendor/hiqlite/src/client/transaction.rs#L34)). At timeout, the app-side future is dropped. The Store contract says a timed-out consensus request may still commit ([`hiqlite retry contract`](../../crates/plurx-core/src/store/hiqlite.rs#L1240)); this map does not prove cancellation of an already-submitted Raft write.

## Model boundary and claims

Faithfully model one request's queue claim, domain lease, exact binding, finite abstract scan result, fenced publication, request completion, lost-ack read, and sequential cleanup. Repeated attempts need reclaim, retry/yield, takeover and completion-ack loss. Define progress as the durable request/waiter becoming terminal, or a named refusal/yield branch; do not use “an item was inserted” or “scan returned” as the useful predicate.

State the premises for useful completion: readable roots, available physical admission, authority, finite filesystem/provider calls, fair queue/publication lock acquisition, eventual Store/Raft reply or explicit timeout outcome, and finite cleanup/join. The source does not guarantee all of these. A blocked filesystem syscall can outlive cancellation, and a lease heartbeat's expiry path still drains its renewal future. These are liveness premises, not timer values to assume away.

No concrete lock cycle was found within this inspected application path. This is not a transitive deadlock proof: lower Raft/network/leader recovery, remote authority construction, kernel filesystem waits and process-runtime shutdown remain outside scope. Ripwire refused because `target` was inaccessible; claims were checked directly. The JSON file is a drift receipt, not a liveness proof.
